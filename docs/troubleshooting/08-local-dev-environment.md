# 08. 로컬 개발 환경에서 평가·검증을 돌리며 겪은 문제들

- 발생일: 2026-11-14 ~ 2026-11-15
- 영향: 평가·E2E 검증이 이미 실행 중인 앱과 충돌하거나, 실행 중인 앱의 상태가 지워질 위험
- 상태: **조치 완료** (검증용 앱 분리 실행, 작업 규칙 정리). 일부는 원인 추정
- 관련: [장애 분석 02 (지속 세션)](02-mqtt-persistent-session-deadlock.md), [ADR-006 (Kafka Streams 상태)](../decisions/ADR-006-kafka-streams-state.md)

8GB M1 노트북 한 대에서 인프라(Kafka·MQTT·SQL Server), 운영처럼 돌아가는 앱, 평가용 앱을 함께 돌리면서 생긴 문제를 모았습니다. 코드 결함은 아니지만 같은 실수를 반복하지 않기 위해 기록합니다.

---

## 1. 8080 포트를 예전 코드의 앱이 점유하고 있었다

### 현상
새 코드로 평가하려고 `bootRun`을 하자 8080이 이미 사용 중이었습니다. 몇 시간 전에 띄운 **예전 코드의 앱**이 계속 돌고 있었고, 그대로 평가하면 새 기능(재생 모드)이 없는 서버를 상대로 평가하게 됩니다.

### 원인
앱을 띄운 터미널이 따로 있었고, 작업 세션에서는 그 프로세스를 종료할 권한이 없었습니다. 그냥 다른 포트로 하나 더 띄우면 **두 앱이 같은 MQTT client-id(`qg-bridge`)와 같은 Kafka 소비자 그룹**을 쓰게 됩니다. MQTT 지속 세션은 같은 ID로 다시 접속하면 기존 연결을 끊어 버리고([장애 분석 02](02-mqtt-persistent-session-deadlock.md)), 같은 소비자 그룹이면 파티션이 두 앱으로 나뉘어 운영 앱의 적재·탐지가 일부 빠집니다.

### 조치
검증용 앱은 **8081에서, 운영 앱과 겹치지 않게** 띄웠습니다.

| 항목 | 운영 앱 (8080) | 검증용 앱 (8081) |
|---|---|---|
| Kafka 소비 (DB 적재·Streams) | 켬 | **끔** (에이전트 API만 사용) |
| MQTT client-id | `qg-bridge` | **`qg-bridge-eval`** |
| 용도 | 평소 데이터 처리 | 재생 평가, E2E 확인 후 종료 |

`qg-bridge-eval` 지속 세션은 브로커에 최대 1시간(`session-expiry-seconds`) 남지만, 그동안 시뮬레이터를 돌리지 않으면 영향이 없습니다.

## 2. `gradlew clean`이 실행 중인 앱의 Kafka Streams 상태를 지웠다

### 현상
검증 중 `./gradlew clean`을 실행해 `qms-app/build`가 통째로 지워졌습니다. 8080 앱은 health UP을 유지했지만, 이 폴더에는 클래스 파일뿐 아니라 **Kafka Streams 상태 저장소(`build/kafka-streams-state`, RocksDB)**도 들어 있습니다.

### 원인
`application.yml`의 `spring.kafka.streams.state-dir`가 `./build/kafka-streams-state`입니다. 빌드 산출물 폴더에 실행 중 상태를 두고 있어서, 빌드 정리가 곧 상태 삭제가 됩니다. 상태는 Kafka changelog 토픽에서 복구되지만([ADR-006](../decisions/ADR-006-kafka-streams-state.md)), **실행 중인 프로세스는 디스크의 RocksDB 파일이 사라진 상태로 계속 돌기 때문에** 다음 상태 기록 때 오류가 날 수 있습니다.

### 조치
- 클래스를 다시 빌드하고, 8080 앱을 재시작해 changelog에서 상태를 복구하도록 했습니다.
- 작업 규칙: **실행 중인 앱이 있으면 `gradlew clean`을 쓰지 않는다.**

### 남은 개선
상태 폴더를 `build/` 밖(예: `./data/kafka-streams-state`)으로 옮기면 빌드 정리와 실행 상태가 분리됩니다. 설정 변경이라 다음 작업 후보로 둡니다.

## 3. 전체 테스트가 운영 앱의 소비자 그룹을 흔들었다

### 현상
`./gradlew test` 전체를 돌리면 `QmsAppApplicationTests`가 앱 컨텍스트 전체를 잠깐 띄웁니다. 이때 같은 소비자 그룹으로 Kafka에 붙기 때문에 8080 앱의 소비자 그룹이 한 번 **재조정(rebalance)**될 수 있습니다.

### 영향과 조치
이번에는 처리 중인 메시지가 없어 영향이 없었습니다. 운영 앱이 돌고 있을 때 전체 테스트를 돌리면 재조정이 생길 수 있다는 점을 기록해 두고, 기능 검증은 해당 테스트 클래스만 지정해 실행했습니다.

### 남은 개선
통합 테스트 프로필에서 Kafka 소비자·Streams를 끄거나 그룹 ID를 바꾸면 이 간섭이 없어집니다.

## 4. 로컬에만 있던 수정과 원격 저장소가 달랐다

### 현상
README에는 `evaluate_agent.py --runs 3`, `--hide-matching-ncr`가 적혀 있었는데, GitHub `main`의 스크립트에는 이 옵션이 없었습니다. 로컬 `main`은 원격보다 커밋 2개 뒤처져 있었습니다.

### 원인
반복 평가와 숨김 실험을 하며 스크립트를 로컬에서 고쳤지만 커밋하지 않은 채, 그 결과를 문서(README)에만 반영해 푸시했습니다.

### 조치
로컬을 원격 `main`으로 빨리 감기한 뒤, 로컬 수정본을 버리지 않고 평가 개편 커밋에 포함했습니다. 이후에는 문서에 적는 옵션은 **같은 PR에서 코드도 함께** 올립니다.

## 5. 긴 작업이 중간에 몇 시간 멈췄다 (원인 추정)

### 현상
자동으로 이어서 개발하던 중, 저녁 이후 몇 시간 동안 커밋·보고가 없었습니다. 이후 작업 세션이 다시 시작되면서 돌던 측정 하나와 8081 검증 앱이 멈춰 있었습니다. 코드와 커밋은 그대로 남아 있었습니다.

### 원인 (추정)
작업이 노트북 위에서 돌기 때문에, 노트북이 잠자기에 들어가면 세션과 프로세스가 함께 멈춥니다. 정확한 원인은 확인하지 못했습니다.

### 조치
- 긴 평가·측정을 돌릴 때는 전원 연결 + 잠자기 끄기, 또는 `caffeinate -dis`를 띄워 둡니다.
- 측정은 끊겨도 처음부터 다시 돌릴 수 있게 실행마다 상태를 초기화하는 구조([장애 분석 04](04-agent-evaluation-leakage.md))를 유지합니다. 이번에도 끊긴 측정만 다시 돌렸습니다.

---

## 배운 점

- **실행 중인 상태를 빌드 산출물 폴더에 두지 않는다.** 빌드 정리와 운영 상태가 한 폴더에 있으면 무심한 명령 하나로 상태가 사라집니다.
- **같은 앱을 두 개 띄울 때는 "외부에서 보이는 정체성"을 나눈다.** 포트만이 아니라 MQTT client-id, Kafka 소비자 그룹이 겹치면 두 앱이 서로의 메시지를 가져갑니다.
- **문서에 적은 것은 코드에도 있어야 한다.** 로컬에만 있는 수정은 다른 사람(또는 다른 세션)이 저장소만 보고 작업할 때 바로 어긋납니다.
