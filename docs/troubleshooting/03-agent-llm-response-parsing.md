# 03. 원인 분석 에이전트의 LLM 호출 실패와 응답 해석 실패

- 발생일: 2026-11-14
- 영향: 에이전트 평가 5건 중 5건 → 4건 실패. 실패한 사례는 분석 결과와 부적합 초안이 만들어지지 않음
- 상태: 조치 완료, **재평가 대기** (결과는 [평가 결과](../evaluation.md)에 반영 예정)

이 문제는 두 단계로 나타났습니다. 첫 번째 문제를 풀자 두 번째 문제가 드러난 경우입니다.

---

## 1단계. 모든 분석이 1초 안에 실패

### 현상
평가 스크립트(`scripts/evaluate_agent.py`)를 실행하자 5건이 모두 `FAILED`였습니다.

| 사례 | 판단 | 도구 호출 | 소요 |
|---|---|---|---|
| 히터 열화 | FAILED | 0 | 1.0초 |
| 압력 센서 이상 | FAILED | 0 | 0.3초 |
| 냉각 막힘 | FAILED | 0 | 0.4초 |
| 체크 링 마모 | FAILED | 0 | 0.4초 |
| 단발성 경보 | FAILED | 0 | 0.4초 |

기록된 오류는 `java.lang.RuntimeException: Failed to generate content` 한 줄뿐이었습니다.

### 원인 분석
**① 숫자에서 실패 지점을 좁혔습니다.**
- 도구 호출이 0회 → 에이전트가 DB 조회를 한 번도 시작하지 못함
- 0.3~1초 만에 종료 → LLM 서버에 첫 요청을 보내자마자 거절됨
- 반면 경보 조회, 사건 묶기(경보 4~6건을 하나로), 실패 기록 저장은 정상
→ **LLM 호출 한 지점**의 문제로 범위를 좁혔습니다.

**② 오류 메시지가 원인을 가리고 있었습니다.**
`Failed to generate content`는 라이브러리가 실제 예외를 감싸서 던진 포장 메시지입니다. 코드가 최상위 예외의 `toString()`만 기록하고 있어서, 그 안의 진짜 원인(인증 실패인지, 모델이 없는지)이 남지 않았습니다.

**③ 설정을 점검했습니다.**
기본 모델이 `gemini-2.5-flash`로 되어 있었는데, 같은 API 키를 쓰는 다른 프로젝트는 더 새로운 모델을 쓰고 있었습니다. 시간이 지나 기본 모델이 이 키로 사용할 수 없는 상태였을 가능성이 컸습니다.

### 조치
| 조치 | 파일 |
|---|---|
| 모델을 `gemini-3.8-flash`로 변경 (`.env`의 `GEMINI_MODEL`, 설정 기본값) | `application.yml`, `.env.example` |
| Gemini 3 계열의 도구 호출 반복에 필요한 사고 서명 사용 (`include-thoughts: true`, Spring AI 문서 권고) | `application.yml` |
| 실패 시 **감싼 원인까지 이어서 기록** (`causeChain`: `A ← B ← C`) | `IncidentAnalyzer.java` |
| 키 값을 노출하지 않고 키·모델을 점검하는 스크립트 추가 (사용 가능한 모델 목록, 생성 요청 결과) | `scripts/check_gemini.sh` |

### 결과
5건 모두 LLM이 응답하고 도구를 5~6회씩 호출하기 시작했습니다. 그중 체크 링 마모 사례는 **원인 정답(`CHECK_RING_WEAR`), 부적합 초안 생성, 확신도 90**으로 성공했습니다. 나머지 4건은 다른 이유로 실패했습니다(2단계).

---

## 2단계. 조사는 끝났지만 마지막 답변을 읽지 못함

### 현상
| 사례 | 판단 | 도구 호출 | 소요 |
|---|---|---|---|
| 히터 열화 | FAILED | 6 | 30.1초 |
| 압력 센서 이상 | FAILED | 5 | 29.1초 |
| 냉각 막힘 | FAILED | 6 | 38.4초 |
| 체크 링 마모 | **NCR_DRAFT (정답)** | 6 | 19.7초 |
| 단발성 경보 | FAILED | 5 | 35.4초 |

1단계에서 추가한 원인 기록 덕분에 이번에는 진짜 오류가 보였습니다.

```
tools.jackson.core.exc.StreamReadException: Unexpected character ('*' (code 42)):
expected a valid value (JSON String, Number, Array, Object or token 'null', 'true' or 'false')
```

### 원인 분석
**① 실패 단계 특정.** 도구를 5~6회 호출하고 수십 초가 걸렸으므로, 조사 절차는 끝까지 수행됐습니다. 실패는 **최종 답변을 Java 객체로 변환하는 단계**에서 났습니다.

**② 오류 메시지 해석.** "JSON 값을 기대했는데 첫 글자가 `*`였다"는 뜻입니다. JSON은 `{`로 시작해야 하는데, 응답이 `*`로 시작했습니다.

**③ `*`의 정체.** 1단계에서 켠 `include-thoughts: true`는 Gemini 3 계열이 모델의 **사고 요약**을 함께 보내게 합니다. 사고 요약은 보통 `**분석 중**`처럼 마크다운 굵은 글씨 제목으로 시작합니다. Spring AI의 자동 변환(`ChatClient...entity(AnalysisResult.class)`)은 응답 텍스트 전체를 JSON으로 읽으려다 첫 글자 `*`에서 실패한 것으로 판단했습니다.

**④ 한 건만 성공한 이유.** 사고 요약이 매번 붙는 것은 아니기 때문입니다. 체크 링 사례는 요약 없이 JSON만 와서 성공한 것으로 보입니다.

1단계의 조치(사고 서명 사용)가 2단계 문제의 원인이 된 셈입니다. 도구 호출 반복에는 필요한 설정이라 끄지 않고, **응답을 받는 쪽을 튼튼하게** 만드는 방향을 택했습니다.

> 실제 응답 원문을 보기 전에 내린 추정입니다. 그래서 아래 조치에 "실패 시 응답 원문 앞부분 기록"을 함께 넣어, 재평가에서 추정이 맞는지 확인할 수 있게 했습니다.

### 조치
응답 형식을 프레임워크의 자동 변환에 맡기지 않고, **직접 받아서 직접 해석**하도록 바꿨습니다.

| 순서 | 내용 |
|---|---|
| 1 | 시스템 프롬프트에 **출력 형식 명시**: "조사를 마친 뒤 마지막 답변은 JSON 객체 하나만. 설명·마크다운·코드 블록 표시 금지" |
| 2 | `entity()` 대신 `chatResponse()`로 **응답 전체 텍스트**를 받음 (사고 요약과 최종 답이 나뉘어 와도 모두 모음) |
| 3 | 코드 블록 표시(```json)를 걷어 내고, `{` 위치를 앞에서부터 차례로 시도해 **`decision`이 들어 있는 JSON 객체**를 찾음 |
| 4 | 그래도 못 찾으면 **도구 없이 1회만** "방금 분석 내용을 JSON으로만 다시 출력"하도록 요청 (조사를 반복하지 않아 비용이 적음, 도구 기록에 `repairJsonFormat()`으로 남김) |
| 5 | 최종 실패 시 **응답 원문 앞부분 300자**를 오류에 기록 |

```java
ChatResponse response = chatClient().prompt()
        .system(AgentPrompts.SYSTEM)          // 출력 형식 명시 포함
        .user(userPrompt)
        .tools(new QualityTools(jdbc, trace, asOf))
        .call()
        .chatResponse();                      // entity() 대신 원문 전체를 받는다
String text = allText(response);
AnalysisResult parsed = parseResult(text);    // 사고 요약 등을 건너뛰고 JSON 만 찾는다
if (parsed == null) {
    // 도구 없이 형식만 다시 요청 (1회)
}
```

### 검증
- JSON 찾기 로직: 사고 요약 안에 `{...}` 같은 중괄호가 섞인 경우에도 실제 결과 JSON을 골라내는지 별도로 시험해 통과
- 코드: 컴파일 점검 통과. 이 과정에서 결과 변수에 값을 두 번 대입해 **트랜잭션 람다 안에서 쓸 수 없게 되는 컴파일 오류**를 발견해 함께 수정
- 전체 재평가: 대기 중

## 재발 방지
- **포장된 예외는 원인까지 기록한다.** 외부 라이브러리의 오류 메시지는 진짜 원인을 감싸고 있는 경우가 많다. 이번에도 원인 기록을 추가한 뒤에야 2단계 문제가 보였다.
- **LLM 출력은 형식이 깨질 수 있다고 가정한다.** 프롬프트로 형식을 요구하더라도, 받는 쪽에서 관대하게 해석하고, 그래도 안 되면 복구를 시도하고, 끝내 실패하면 원문을 남긴다.
- **설정 하나를 바꾸면 그 부작용까지 확인한다.** 도구 호출을 위해 켠 `include-thoughts`가 응답 형식에 영향을 줬다.
- **평가 스크립트를 먼저 만든 덕분에** 실패 패턴(소요 시간, 도구 호출 수)을 숫자로 보고 문제 지점을 빠르게 좁힐 수 있었다.

## 배운 점
LLM 에이전트는 "모델이 똑똑한가"보다 **모델과 프로그램 사이의 경계**에서 더 자주 실패한다. 모델 이름·인증·응답 형식처럼 사소해 보이는 연결 부분을 단계별로 확인하고, 실패했을 때 무엇이 왔는지 남겨 두는 것이 문제를 빨리 푸는 방법이었다.
