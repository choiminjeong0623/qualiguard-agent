# 가드레일 및 폴백 정책서

| 항목 | 내용 |
|---|---|
| 대상 | 원인 분석 에이전트 파이프라인(분류 → 분석 → 검증 → 작성 → 승인·연계)과 MCP 서버 |
| 목적 | 무한 반복·비용 폭주·지어낸 근거·잘못된 자동 처리를 막고, 막혔을 때 어디로 넘길지 정한다 |
| 관련 결정 | ADR-005, 008, 010, 016, 020 · [장애 대응 10](../troubleshooting/10-llm-timeout-retry.md) |
| 기준 | main, 2026-11-23. 값은 `application.yml` 기본값 |

## 1. 원칙

1. **AI 는 초안까지, 확정은 사람.** 부적합 확정과 MES/ERP 전달은 사람의 승인 버튼을 거친다.
2. **모든 반복에는 숫자 상한이 있다.** 상한에 닿으면 멈추고, 멈춘 사실을 기록하고, 사람에게 보이게 한다.
3. **실패는 조용히 끝내지 않는다.** 실패한 경보는 다시 분석 대상으로 돌아가거나 판단 보류 목록에 오른다.
4. **판정은 규칙, 설명은 LLM.** 보류 여부·검증 통과 여부·상한은 코드가 정한다(ADR-020 "정하는 것은 규칙으로").

## 2. 가드레일 목록

### 2.1 반복·비용 상한 (무한 루프 방지)

| ID | 가드레일 | 값 (설정 키) | 넘으면 | 코드 |
|---|---|---|---|---|
| G-01 | LLM 호출 시간 제한·재시도 | 90초, 재시도 1회, 2초 뒤 (`qg.agent.llm.*`). 401·403 은 재시도 없이 실패 | 사건 FAILED, 경보는 NEW 로 되돌아가 다시 분석 대상 | `LlmCallPolicy` |
| G-02 | JSON 형식 복구 | 1회, 도구 없이 (`repair-v1.md`) | 사건 FAILED | `IncidentAnalyzer` |
| G-03 | **분석 1회 안의 도구 호출 수** | 15회 (`qg.agent.max-tool-calls`, 0 이면 끔) | DB 를 조회하지 않고 "지금까지 근거로 결론을 내라" 오류를 돌려줌. 그래도 계속 부르면 G-01 시간 제한이 마지막 상한 | `ToolCallLimit` |
| G-04 | 검증 반려 뒤 재분석 | 1회 (`verify-max-retries`) | 결과를 쓰되 `verify_status=WEAK` 표시 → G-10 판단 보류 조건 | `IncidentOrchestrator` |
| G-05 | 관찰(OBSERVE) 뒤 재확인 | 40 shot 마다, 최대 3회 (`recheck-shots`, `recheck-max`) | 더 재확인하지 않고 판단 보류(RECHECK_LIMIT) | `AgentScheduler`, `JudgementHoldPolicy` |
| G-06 | 하루 토큰 예산 | 1,000,000 (`budget.daily-tokens`) | 자동 분석을 다음 날 0시까지 멈춤. 사람이 누르는 수동 분석은 허용 | `TokenBudget`, `GET /api/agent/budget` |
| G-07 | 같은 경보 반복 실패 | 2번 실패한 경보는 자동 선택에서 건너뜀 | 경보 목록에 남아 사람이 확인 | `IncidentAnalyzer.nextSeed` |
| G-08 | 재시작 복구 기한 | 마지막 기록 뒤 1440분 (`pipeline.recover-max-age-minutes`) | 이어 하지 않고 FAILED | `IncidentOrchestrator.resume` |

G-03 기본값 15의 근거: 현재 프롬프트의 조사 절차는 6단계(추이는 넓게·좁게 2번)라 보통 7~9회이고, 마지막 측정에서 분석 7단계 도구 호출 합계 51회(단계당 평균 약 7.3회)였습니다. 두 배 여유를 두었습니다.

### 2.2 근거·환각 통제

| ID | 가드레일 | 방법 | 막히면 |
|---|---|---|---|
| G-09 | 기준 시각 고정 | 공정 조회 도구에 서버가 asOf 를 넣고 모델에게 노출하지 않음 | — (구조적 차단) |
| G-10 | 근거 수치 대조 | 검증 에이전트(규칙, LLM 아님)가 근거 수치를 도구가 실제로 돌려준 값과 대조(규칙 6)하고, 조사 생략·지속성 경보를 NOISE 로 판단·watchItems 누락 같은 모순도 확인 | 지적을 붙여 재분석(G-04) |
| G-11 | 인용 실재 확인 | 유사 사례 번호는 검색 결과에 있는 것만, SOP 번호는 검색 결과에 있는 것만(프롬프트 지시 + 검증) | 재분석 |
| G-12 | 도구 오류 반환 | 예외 대신 `{"error"}` 를 모델에 돌려 인자를 고치게 함 | 모델이 고치지 못하면 G-03·G-01 |
| G-13 | 특정 고장 힌트 금지 | 프롬프트에 원인-센서 대응표를 넣지 않음. 과거 사례를 도구로 찾아 추론 | — (설계 원칙) |

### 2.3 사람에게 제어권 넘기기 (Human-in-the-loop)

| ID | 언제 | 어디로 | 사람이 하는 일 |
|---|---|---|---|
| H-01 | 부적합 초안이 만들어지면 항상 | QMS 부적합 검토 화면 (AWAITING_APPROVAL) | 근거 확인 → 수정 → 승인 또는 반려. 승인해야 아웃박스로 MES/ERP 전달 |
| H-02 | 재확인 상한까지 관찰이 이어짐 (RECHECK_LIMIT) | 판단 보류 목록 | 현장 확인 후 처리 메모 → 다음 분석의 reviewerNotes |
| H-03 | 검증 WEAK 인데 결론이 초안이 아님 (VERIFY_WEAK) | 판단 보류 목록 | 위와 같음 |
| H-04 | 자동 조치(기본 꺼짐)가 한도를 넘음 | 조치 승인 대기 | 설비별 24시간 3회 초과, 효과 없는 조치 2회 초과 시 사람이 결정 |
| H-05 | ML 먼저 모드(기본 꺼짐)에서 낯선 경보 | LLM 분석으로 넘김 | 학습 분포 밖이면 확률이 높아도 ML 판단 생략 안 함, 10% 는 LLM 과 비교 기록 |

### 2.4 접근·대체 경로

| ID | 가드레일 | 내용 |
|---|---|---|
| G-14 | API 인증 | `/api/agent`·`/actuator` 는 REVIEWER 로그인 또는 `Bearer QG_AGENT_API_TOKEN`, `/mcp` 는 토큰만 |
| G-15 | 보고서 작성 폴백 | 로컬 모델 작성(선택)이 120초를 넘거나 실패하면 클라우드로 넘기지 않고 근거 표(템플릿) 초안 |

## 3. 상태별 결과 요약

| 상황 | 사건 결과 | 경보 | 사람에게 보이는 곳 |
|---|---|---|---|
| 정상 + 초안 | AWAITING_APPROVAL | NCR_DRAFTED | 부적합 검토 |
| 정상 + 관찰·센서 점검 | CLOSED | DISMISSED | 에이전트 조치 기록 |
| 검증 WEAK + 초안 아님 | CLOSED + 보류 | DISMISSED | 판단 보류 카드 |
| LLM 실패·형식 실패 | FAILED | NEW (다시 분석) | 경보 목록, 로그 |
| 예산 소진 | 새 사건 안 만듦 | NEW 그대로 | `GET /api/agent/budget` |

## 4. 구현하지 않은 항목

| 항목 | 현재 | 위험 | 다음 단계 |
|---|---|---|---|
| 민감 정보 필터 | 없음. 정비 이력의 담당자 이름(`technician`, 합성 데이터는 "김OO")이 외부 LLM 으로 나감 | 실제 공장 데이터면 개인정보·공정 정보가 클라우드로 나감 | 도구 결과에서 담당자 컬럼 제외, 공정 수치는 폐쇄망 모드(G-16)로 |
| 프롬프트 인젝션 방어 | 검토자 메모·과거 NCR 문장이 그대로 모델에 들어감. "메모만으로 결론 내지 말라" 지시만 있음 | 악의적 메모가 판단을 흔들 수 있음 (작성자는 로그인한 REVIEWER 로 제한) | 메모 길이 제한, 지시문 패턴 탐지 |
| 출력 내용 필터 | JSON 형식·결정 값·원인 코드 목록만 검사 | 부적절한 권고 문장 | 권고 조치 문장을 SOP 절차와 대조 |
| 도구 호출 상한 측정 | G-03 은 코드 시험으로만 확인 | 상한 15가 정상 분석을 막는지 실측 안 됨 | 재생 평가에서 상한 도달 횟수 확인 (trace 의 "도구 호출 상한" 줄) |
