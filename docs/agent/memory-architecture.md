| 항목 | 내용 |
|---|---|
| 대상 | 원인 분석 에이전트가 "이전에 무엇을 봤고 판단했는지"를 다음 분석에 넘기는 구조 |

## 1. 전제: 대화형 에이전트가 아니다

QualiGuard 에이전트는 사람과 대화하지 않습니다. 경보 하나(사건)를 받아 조사하고 JSON 판단을 내는 **작업형 에이전트**입니다.
그래서 "대화 컨텍스트 창 관리·요약"이나 "사용자 선호 기억"은 두지 않았고, 대신 **같은 설비에서 앞서 내린 판단**과 **사람이 승인한 지식**을 기억으로 씁니다.

## 2. 기억 계층

| 구분 | 무엇 | 저장소 | 넣는 곳 | 범위·갱신 | 수명 |
|---|---|---|---|---|---|
| 작업 기억 | 분석 1회 안의 도구 결과 | LLM 컨텍스트 (Spring AI 도구 호출 루프) | 모델 입력 | 분석 1회. 도구 호출 상한 15회 | 분석이 끝나면 버림 (trace 는 `agent_analysis.tool_trace` 로 남김) |
| 사건 상태 | 사건 단계·시도 번호·프롬프트·분석·검증 결과 | `agent_incident.checkpoint_json`, `agent_incident_event` | 오케스트레이터 | 상태가 바뀔 때마다 | 앱 재시작 시 복구. 1440분 지나면 FAILED |
| 단기 기억 ① 이전 판단 | 같은 설비의 앞선 판단(결정·원인·확신도·watchItems) | `agent_analysis` | 사용자 프롬프트 `previousJudgements` | 최근 3건, `merge-minutes`(60분) 안, 같은 run_tag, **기준 시각 이전만** | DB 영구, 읽기 범위만 제한 |
| 단기 기억 ② 검토자 메모 | 판단 보류를 처리한 사람이 남긴 현장 확인 메모 | `agent_analysis.hold_note` | 사용자 프롬프트 `reviewerNotes` | 같은 설비, 처리 완료(RESOLVED), 최근 3건, 기준 시각 이전만. **평가 실행에는 넣지 않음** | DB 영구 |
| 검증 근거 | 도구가 돌려준 수치 | `ToolObservations` (메모리, 사건 단위) | 검증 에이전트 | 사건의 모든 시도 누적, 최대 5,000개 | 사건 종료 시 버림 |
| 장기 기억 ① 승인 사례 | 사람이 작성했거나 AI 초안을 사람이 승인한 NCR | `ncr` + `ncr_embedding`(VECTOR 768) | 도구 `findSimilarNcr` | 승인·종결 상태만, **기준 시각까지 승인된 것만** | 영구. 임베딩은 60초마다 새 사례만 생성(text_hash 로 변경 감지) |
| 장기 기억 ② 절차 지식 | SOP·설비 매뉴얼 | 마크다운 파일 → `SopLibrary`(BM25) | 도구 `searchSop` | "## 절" 단위 조각 | 앱 시작 시 색인 |
| 장기 기억 ③ 정비 이력 | 부품 교체·수리 기록 | `maintenance_history` | 도구 `getMaintenanceHistory` | 최근 10건 | 영구 |

## 3. 설계 원칙

1. **기억도 기준 시각을 지킨다.** 이전 판단·검토자 메모·승인 사례 모두 "분석 기준 시각 이전"만 읽습니다. 나중에 승인된 사례를 지난 경보 분석에 쓰면 평가가 부풀려지는 것을 실제로 겪었습니다([장애 분석 04](../troubleshooting/04-agent-evaluation-leakage.md), [06](../troubleshooting/06-knowledge-base-future-leakage.md)).
2. **사람이 확인한 것만 장기 기억이 된다.** AI 초안은 사람이 승인해야 지식저장소에 들어갑니다(`source` 로 구분). 반려·보류된 판단은 들어가지 않습니다.
3. **기억은 근거가 아니라 단서다.** 프롬프트가 "이전 판단을 그대로 반복하지 말고 새로 확인된 것을 밝혀라", "검토자 메모만으로 결론을 정하지 말고 데이터가 다르면 데이터를 따르라"고 지시합니다.
4. **평가와 운영의 기억을 나눈다.** `run_tag` 가 다른 기록은 서로 섞이지 않고, 사람 메모는 평가 실행에 넣지 않아 채점에 영향을 주지 않습니다.

## 4. 컨텍스트 크기

| 항목 | 값 | 출처 |
|---|---|---|
| 분석 1단계 입력 토큰 평균 | 26,398 | `eval/results/20261123-1211_*/summary.md` (7단계) |
| 출력 토큰 평균 | 1,113 | 같은 파일 |
| 이전 판단·검토자 메모 | 각 최대 3건 | 코드 상수 |
| 하루 토큰 예산 | 1,000,000 | `qg.agent.budget.daily-tokens` |

입력의 대부분은 도구 결과입니다. 요약 정책 대신 **도구가 구간 평균으로 묶어 돌려주는 방식**(예: 300 shot 을 20 shot 씩 15구간)으로 크기를 제한합니다.

## 5. 하지 않은 것과 이유

| 항목 | 이유 | 다시 검토할 조건 |
|---|---|---|
| 대화 요약·슬라이딩 윈도우 | 대화가 없고 분석 1회 입력이 약 2.6만 토큰으로 모델 한계보다 충분히 작음 | 도구 결과가 커져 입력이 10만 토큰을 넘을 때 |
| 사용자별 선호 기억 | 판단 주체가 개인이 아니라 품질 조직 | 검토자별 보고서 문체 맞춤이 필요할 때 |
| 이전 판단을 벡터로 검색 | 같은 설비·최근 60분이면 시간 순 3건으로 충분 | 여러 설비에 걸친 연쇄 고장을 다룰 때 |
| 반려 사유를 기억으로 쓰기 | 반려 사유는 아직 구조화돼 있지 않음 | 반려 사유 분류가 생기면 "하지 말 것" 기억으로 |
