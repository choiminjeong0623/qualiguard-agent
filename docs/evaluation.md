## 2. 결과

### 2-1. 고장 탐지

| 고장 | 시작 | 첫 경보 | 탐지 지연 | 첫 경보 규칙 | 고장 구간 불량 | 첫 경보 **이전** 불량 |
|---|---|---|---|---|---|---|
| 히터 열화 | 300 | 345 | 45 shot | X̄: 실린더 온도 | 194 | **0** |
| 냉각 막힘 | 900 | 935 | 35 shot | X̄: 사이클 타임 | 217 | **0** |
| 체크 링 마모 | 1200 | 1235 | 35 shot | X̄: 쿠션량 | 232 | **0** |
| 압력 센서 이상 | 400 | 407 | 7 shot | 개별값: 사출 압력 | 0 | 0 |

- 실제 고장 3종을 **모두 첫 불량이 발생하기 전에** 감지했습니다. 고장 구간 불량 643건이 전부 첫 경보 이후에 발생했으므로, 경보 시점에 조치했다면 이론상 모두 막을 수 있었습니다.
- 경보에 담긴 z 점수가 고장의 특징을 보여 줍니다. 예: 히터 열화 첫 경보 시 실린더 온도 **−5.06σ**, 사출 압력 +1.89σ, 모터 전류 +1.90σ / 냉각 막힘 첫 경보 시 금형 온도 **+3.99σ**, 사이클 타임 +3.47σ
- 압력 센서 이상은 경보가 났지만 품질 영향이 없습니다. 이 경보를 에이전트가 "공정이 아닌 센서 문제"로 구분하는지가 다음 단계의 평가 항목입니다.

**seed 5개 재현 평가 (로드맵 E2, [`eval/detection_report.md`](../eval/detection_report.md))** — 위 표는 seed 42 한 번의 결과입니다. `cd qms-app && ./gradlew detectionEval` 은 시뮬레이터를 seed 1~5 로 파일 출력해 결측·중복·늦은 메시지가 섞인 그대로 같은 `SpcEngine` 에 재생하고, 50 shot 창 단위로 채점합니다.

| 지표 (seed 5개 평균 ± 표준편차) | 값 |
|---|---|
| 정밀도 / 재현율 / F1 | 0.947 ± 0.035 / 0.865 ± 0.022 / 0.904 ± 0.014 |
| 오경보율(FPR) / 놓침률(FNR) | 0.056 ± 0.039 / 0.135 ± 0.022 |
| 고장 4종 탐지율 | 각 5/5 |
| 첫 불량 전 탐지 | 히터 3/5, 냉각 2/5, 체크 링 3/5, 압력 센서 5/5 |

seed 42 에서는 고장 3종 모두 첫 불량 전에 잡았지만, seed 를 바꾸고 결측을 섞으면 **절반 정도만 첫 불량 전**입니다. 탐지 지연이 30~40 shot 인데 고장 초반에도 불량이 드물게 나기 때문입니다(평상시 불량 약 0.6% 가 섞일 수도 있음). 위 "모두 첫 불량 전" 문장은 seed 42 한 번에만 해당합니다. 탐지를 앞당기는 비교(EWMA)는 로드맵 A4 에서 이 평가기를 재사용해 측정합니다.

**EWMA 관리도 비교 (로드맵 A4, [`eval/ewma_report.md`](../eval/ewma_report.md), `./gradlew ewmaEval`)** — 같은 seed 5개·같은 채점으로, 센서별 EWMA(기준 100 shot, 한계 μ ± L·σ_z)를 지금 규칙에 더했을 때를 비교했습니다. 운영 코드는 바꾸지 않았습니다.

| 방식 | F1 | 오경보율(FPR) | 탐지 지연(shot): 체크 링 / 냉각 / 히터 | 첫 불량 전 탐지: 체크 링 / 냉각 / 히터 |
|---|---:|---:|---|---|
| 지금 규칙 | 0.904 | 0.056 | 31.4 / 34.4 / 39.0 | 3/5 · 2/5 · 3/5 |
| + EWMA λ 0.2, L 3.0 (교과서 기본값) | 0.765 | 0.567 | 14.4 / 15.4 / 18.6 | 3/5 · 5/5 · 4/5 |
| + EWMA λ 0.2, L 4.0 | 0.891 | 0.106 | 24.0 / 27.6 / 26.8 | 3/5 · 3/5 · 4/5 |

- 기본값(L 3.0)은 탐지가 절반으로 빨라지지만 정상 창의 57% 에서 오경보가 납니다. 센서 7개를 각각 보므로 센서 하나의 오경보 간격(평균 수백 shot)이 설비 전체로는 수십 shot 으로 줄어들기 때문입니다.
- 한계를 넓힌 L 4.0 을 더하면 F1 은 거의 같고(0.904 → 0.891), 오경보율은 0.056 → 0.106 으로 두 배, 서서히 진행되는 고장 3종의 탐지는 7~12 shot 빨라집니다.
- **결정 (2026-11-23): 채택하지 않음.** 운영 탐지 규칙은 그대로 둡니다. F1 이 오르지 않았고(0.904 → 0.891), 오경보가 두 배가 되면 LLM 분석 호출과 검토 부담도 두 배 가까이 늘어납니다. 마감 직전에 탐지를 바꾸면 에이전트 평가(E3)의 기준선도 달라집니다. 탐지를 앞당기는 것이 더 중요해지면(예: 불량 비용이 큰 제품) 'L 4.0 추가'를 다시 검토합니다.

### 2-8. 원인 분석 에이전트

**방법 (2026-11-15 개편: 시간 순 재생 평가).** `scripts/evaluate_agent.py`가 사례(고장 4종 + 고장과 떨어진 단발성 경보)마다 경보를 **발생 순서대로** 에이전트에게 분석시키고, 정확한 진단이 언제 나오는지 잽니다.
- 사례를 시작할 때 그 사례 경보의 상태를 모두 미처리로 되돌려 **실행마다 같은 조건**에서 시작합니다.
- 아직 처리되지 않은 가장 이른 경보를 시작점으로 분석합니다(`replay=true`). 에이전트는 **그 경보 시각까지 발생한 경보와 데이터만** 봅니다 ([ADR-007](decisions/ADR-007-sqlserver-qms-schema.md) 결정 4, [장애 분석 04](troubleshooting/04-agent-evaluation-leakage.md)).
- "관찰" 판단 뒤 다음 경보를 분석할 때는 같은 실행의 **이전 판단(판단·원인·확신도·요약·다음에 확인할 항목)**을 함께 넘깁니다.
- 정답이 나오면 멈춥니다(최대 5단계). 정답: 고장은 부적합 초안(NCR_DRAFT) + 정답 원인, 센서 이상은 센서 점검(SENSOR_CHECK), 단발성 경보는 관찰(OBSERVE).
- 지표: 진단까지 걸린 shot 수(고장 시작 기준), 진단 시점까지 불량 수(시뮬레이터 정답 파일), 잘못 만든 초안 수, 진단까지 LLM 호출 수(분석 단계 수 + JSON 재요청).

아래 첫 평가와 반복 평가는 개편 **전** 방식(사례마다 첫 경보 하나만 분석)의 기록입니다.

> ⚠️ **정정 (2026-11-15)**: 아래 첫 평가의 5/5는 사건 묶기 과정에서 **첫 경보 이후의 경보까지 함께 분석한, 실제 운영보다 유리한 조건**의 결과였습니다. 반복 평가에서 이 점이 드러났고, 원인 분석과 조치는 [장애 분석 04](troubleshooting/04-agent-evaluation-leakage.md)에 있습니다.

체크 링은 첫 경보(shot 1235)와 첫 불량(shot 1239) 사이가 4 shot 이라, 첫 경보에서 바로 초안을 써야만 "첫 불량 전"이 됩니다. 첫 경보 시점에는 쿠션량 평균 이동만 있고 불량이 없어, 일반 원칙(근거가 일부면 확신도 50~79, 품질 영향이 보이면 초안)으로는 관찰이 합리적인 판단입니다. 다음 경보(shot 1239, 4 shot 뒤)에서 바로 초안으로 바꿨습니다. 이를 첫 경보에서 초안으로 만들려면 "쿠션량이 움직이면 체크 링"처럼 **특정 고장에 맞춘 힌트**가 필요한데, 이는 하지 않기로 한 일입니다. 재확인 간격도 다음 경보가 4 shot 뒤라 효과가 없습니다. 앞당기려면 탐지 단계(예: 쿠션량에 EWMA·CUSUM 처럼 작은 이동에 민감한 관리도)를 바꿔야 하며, 오경보와의 균형을 따로 측정해야 합니다 → [향후 계획](future-work.md).

### 2-9. 공개 실제 데이터 보조 검증 (UCI SECOM)

**목적.** 합성 데이터에서 잘 동작한 SPC 탐지 규칙이 실제 공정 데이터에서도 의미가 있는지 봅니다 ([ADR-002](decisions/ADR-002-synthetic-data.md) 보조 실험).

**방법.** `./scripts/fetch_secom.sh` 로 UCI SECOM(반도체 공정 센서 590개 × 1,567건, 합격/불합격 라벨)을 받고(데이터는 커밋하지 않음), `cd qms-app && ./gradlew secomValidation` 으로 **시뮬레이터와 같은 `SpcEngine`(같은 규칙·같은 기준 구간 100건)** 에 시간 순으로 넣었습니다. 바꾼 것은 센서 목록뿐입니다: 기준 구간에서 절반 넘게 비었거나 값이 하나뿐인 센서는 기준을 잡을 수 없어 제외했습니다.

**결과 (2026-11-15).**
- 센서 590개 중 448개 사용 (절반 넘게 빈 센서 20개, 값이 하나뿐인 센서 122개 제외), 감시 구간 1,467건 (불합격 87, 합격 1,380)

| 지표 | 불합격 건 | 합격 건 |
|---|---|---|
| 그 건에서 센서 경보 | 46/87 (52.9%) | 887/1,380 (64.3%) |
| 직전 10건 안에 센서 경보 | 87/87 (100%) | 1,379/1,380 (99.9%) |

- 센서 경보 3,005건, 경보가 난 센서 369개 — **100건당 205건**으로 경보가 넘칩니다 (개별값 1,732·X̄ 750·S 523)
- 센서 경보가 난 건 중 불합격 비율 4.9%로, 감시 구간 전체 불합격 비율(5.9%)보다 오히려 낮습니다 → **센서별 SPC 경보는 불합격을 가려내지 못했습니다**
- p 관리도(불합격률) 경보 0건: 기준 구간 처음 100건의 불합격률이 17%로 높아(감시 구간 5.9%) 관리 상한이 높게 잡혔습니다

**해석.** 시뮬레이터에서는 센서 7개가 각각 의미 있고, 고장이 특정 센서를 서서히 움직이도록 설계되어 센서별 관리도가 잘 맞았습니다. SECOM 은
- 센서가 수백 개라 센서마다 독립적으로 ±3~4σ 를 보면 정상 변동만으로도 경보가 쏟아지고 (다중 비교),
- 처음 100건만으로 정한 기준이 공정의 정상 변동(날짜에 따른 이동)을 담지 못하며,
- 위 결과처럼 불합격 건과 합격 건의 경보 비율이 비슷해, 불합격이 개별 센서 하나의 이탈로는 드러나지 않는 것으로 보입니다.

따라서 **이 프로젝트의 탐지 규칙은 "의미가 알려진 소수 센서, 서서히 진행하는 고장"에 맞춘 것이며, 수백 개 센서의 실제 공정에 그대로 옮길 수 없습니다.** 실제 적용에는 센서 고르기(공정 지식·변수 중요도), 다변량 관리도(Hotelling T², PCA 기반 SPE)나 기준 구간 갱신이 필요합니다. 결과를 좋게 보이도록 SECOM 에 맞춰 규칙을 조정하지는 않았습니다.

**다변량 관리도 시험 (로드맵 A4 후반, `cd qms-app && ./gradlew secomT2`).** 위 '다변량 관리도가 필요하다'를 직접 확인하는 도구입니다. 센서 수(448)가 기준 건수(100)보다 많아 공분산 역행렬이 없으므로, 기준 구간 PCA 로 분산 90% 를 설명하는 주성분만 남겨 Hotelling T²(주성분 안의 이상)와 SPE(상관 구조가 깨진 이상)를 계산하고, 기준 구간 99 백분위를 한계로 씁니다. 기준 구간 100건과 300건 두 가지로 불합격·합격 건의 경보 비율, 경보 중 불합격 비율, AUC 를 냅니다. 계산은 단위 시험(`SecomT2Test`: 야코비 고유값, 합성 공정에서 주성분 이동은 T², 상관 깨짐은 SPE 가 AUC 0.9 넘게 구분)으로 확인했고, **SECOM 실제 수치는 데이터가 있는 맥에서 실행해 채웁니다** (클라우드 작업 환경은 UCI 사이트 접근이 막혀 있음).

**다변량 이상 탐지 MEWMA (`cd qms-app && ./gradlew mewmaEval` → `eval/mewma_report.md`).** 센서 7개를 하나의 통계량(T²)으로 보는 MEWMA 를 E2 와 같은 seed 5개·같은 채점으로 비교했습니다. 운영 SpcEngine 이 걸러 낸 깨끗한 값을 넣고, 기준 100 shot 으로 평균·공분산을 정하며, 한계 h 는 센서 7개 χ² 의 상위 0.01%(29.9)·0.001%(35.3)입니다.

| 방식 | F1 | 오경보율 | 체크 링 | 냉각 막힘 | 히터 열화 | 압력 센서 |
|---|---:|---:|---:|---:|---:|---:|
| 지금 규칙 | 0.904 | 0.056 | 31.4 | 34.4 | 39.0 | 12.0 |
| + MEWMA λ0.2 h35.3 | 0.895 | 0.083 | 26.4 | 28.2 | 27.2 | 12.0 |
| + MEWMA λ0.1 h29.9 | 0.866 | 0.172 | 22.2 | 21.8 | 25.6 | 9.8 |

(지연은 고장 시작부터 첫 경보까지 shot, seed 평균)

- 서서히 진행되는 고장 3종의 탐지가 5~13 shot 빨라졌습니다. 같은 오경보 증가에서 센서별 EWMA(λ0.2 L4.0: 오경보 0.106, 7~12 shot 단축)보다 낫습니다.
- MEWMA 단독은 재현율 0.45 로 지금 규칙을 대신할 수 없습니다 (불량률 관리도·단발 규칙이 없음).
- 경보마다 T² 를 센서별로 나눈 기여도를 붙였고, 가장 큰 센서가 고장과 맞았습니다 (히터 → 실린더 온도, 냉각 → 사이클 타임, 체크 링 → 쿠션, 스파이크 → 사출 압력). 정상 구간 오경보는 쿠션이 가장 많았습니다.
- **결정**: 경보 판정은 지금 규칙 그대로 두고, `qg.quality.mewma.mode=shadow` 로 SPC 옆에서 함께 계산해 로그(`[다변량 shadow]`)와 지표(`qg.spc.mewma_shadow_alarms`)로만 남깁니다 (기본 off). 실제 설비 데이터에서 오경보를 먼저 재고 경보에 더할지 정합니다. shadow 상태는 메모리에 있어 앱을 재시작하면 기준 100 shot 을 다시 배웁니다.

**현장 표준 절차(SOP) 검색 (`SopLibrary`, 에이전트 도구 `searchSop`).** 원인을 추정한 뒤 권고 조치를 현장 절차에 맞추도록 가상 SOP 10개(`qms-app/src/main/resources/sop/`, 고장 4종·새 고장 3종·격리·불량 유형별 조치)를 만들고 검색 도구를 붙였습니다. 폐쇄망을 전제로 임베딩 API·벡터 DB 없이 앱 안에서 BM25(한글 두 글자 단위, 센서 키는 한글 이름도 함께)로 찾습니다. 에이전트가 쓸 법한 현상 요약 질의 12개(문서 문장을 베끼지 않음)에서 **맞는 문서를 첫째로 12/12** 찾았습니다 (`SopLibraryTest`). 에이전트는 `recommendedAction` 에 문서 번호를 함께 적습니다 (예: "히터 밴드 저항 측정 (SOP-INJ-010 2절)"). 회사 문서는 `qg.knowledge.sop.dir` 폴더에 마크다운으로 넣으면 함께 색인됩니다. 한계: 질의가 짧으면(예: "cushion 감소") 짧은 공통 문서(불량 유형별 조치표)가 먼저 나올 수 있고, 문서가 수백 개로 늘면 의미 검색(로컬 임베딩)을 더해야 합니다. 실제 분석 품질에 주는 영향은 E3 재평가에서 확인합니다.

**폐쇄망 분석 모드 (`SPRING_PROFILES_ACTIVE=closed`, `./scripts/ab_eval.sh closed [회차]`).** 원인 분석 전체를 외부 API 없이 돌리는 설정입니다. 분석·보류 요약·JSON 고치기는 Ollama 로컬 모델(기본 `qwen2.5:7b`, 도구 호출을 지원하는 모델이어야 함), 유사 사례는 키워드 검색, 보고서 문장은 로컬 작성, SOP 검색은 원래 앱 안에서 합니다. 설정은 `application-closed.yml` 한 곳이고 코드는 같습니다 (`spring.ai.model.chat` 으로 채팅 모델을 고름). 기본 설정은 Gemini 만, closed 는 Ollama 만 만들어지는 것을 `ChatModelSelectionTest` 가 실제 설정 파일로 확인합니다. 로컬 모델은 느리므로 호출 시간 제한을 300초로 늘렸고, 실행 중에 모델을 내려받지 않습니다(`ollama pull` 을 미리). `ab_eval.sh closed` 는 같은 재생 평가를 Gemini 와 로컬 모델로 한 번씩 돌려 `eval/ab_closed.md` 에 정답률·잘못된 초안·지연·토큰을 나란히 적습니다 (로컬 모델 비용은 0으로 계산). **수치는 맥에서 실행해 채웁니다.** 8GB 맥은 SQL Server·Kafka 와 함께 돌리면 7B 모델이 빠듯하므로 `QG_LOCAL_MODEL=qwen2.5:3b` 로 먼저 재는 것을 권합니다.

## 3. 한계

- **합성 데이터**: 고장이 서서히 진행되도록 설계했기 때문에 조기 감지에 유리합니다. 갑자기 발생하는 고장이나 실제 공정의 복잡한 상호작용에서는 결과가 다를 수 있습니다.
- **기준 구간**: 처음 100 shot이 정상이라고 가정합니다. 기준 구간에 이상이 섞이면 관리 한계가 넓어집니다. 실무에서는 검증된 정상 구간이나 검사 규격으로 기준을 정해야 합니다.
- **단발성 오경보**: ±4σ 단일 값 규칙은 정상 데이터에서도 드물게 걸립니다. 에이전트의 판단과 사람의 승인으로 걸러내는 구조로 보완합니다.
- **에이전트 평가의 유리한 조건**: 지식저장소에 시뮬레이터 고장과 원인이 같은 과거 사례가 들어 있습니다. 과거 사례와 정비 이력까지 숨긴 "처음 보는 고장" 실험에서도 25/25였지만, 고장 시나리오 4종은 센서 패턴이 서로 뚜렷이 다르게 설계된 합성 데이터라 실제로 처음 보는 고장에서는 더 어려울 수 있습니다.
- **에이전트 평가 표본**: 사례 5건, 시나리오 데이터 1벌을 3회씩 반복했습니다. 같은 데이터로 반복했기 때문에 진단 시점이 거의 같게 나옵니다. 다른 고장 강도·시작 시점에서는 결과가 달라질 수 있습니다.
- **실제 데이터 일반화**: 공개 실제 데이터(UCI SECOM, 센서 448개)에 같은 규칙을 적용하면 경보가 100건당 205건으로 넘치고 불합격을 가려내지 못했습니다(2-9절). 탐지 규칙은 의미가 알려진 소수 센서에 맞춘 것입니다.

### AI 초안 검토 지표 계산 방법 (로드맵 P3)

사람이 AI 초안을 **얼마나 고쳐서** 승인했는지를 봅니다. 초안 원문을 따로 저장하지 않고, 검토 이력(`ncr_history` 의 EDIT, 바뀐 항목마다 `before`·`after`)에서 되살립니다.

- 항목마다 **처음 고친 이력의 `before`** 가 AI 가 쓴 원문입니다. 수정은 초안(DRAFT) 상태에서만 되므로 그 전에 값이 바뀔 길이 없습니다.
- 원문과 최종값이 다르면 그 항목은 "수정됨"입니다. 고쳤다가 원래대로 되돌렸으면 수정하지 않은 것으로 봅니다.
- 대상: `created_by = 'AGENT'` 인 부적합 중 결정이 난 것 (APPROVED·CLOSED = 승인, REJECTED = 반려). 아직 초안인 것은 `pending` 으로 따로 셉니다.

| 지표 | 뜻 |
|---|---|
| `rejectionRate` | 결정된 초안 가운데 반려 비율 |
| `asIsRate` | 승인된 초안 가운데 한 항목도 고치지 않은 비율 (높을수록 초안을 믿고 쓸 수 있음) |
| `editRate` | 승인된 초안 가운데 하나라도 고친 비율 (= 1 − asIsRate) |
| `avgFieldsChanged` | 승인 1건당 고친 항목 수 평균 |
| `fieldChangeRate` | 항목별 수정 비율. 예: `causeCode` 가 높으면 원인 판단 자체가 자주 틀린 것, `title` 만 높으면 문장 다듬기 |

한계: 승인 전에 고친 것만 셉니다. 승인 뒤 조치 완료(CLOSED)에서 적는 조치 내용은 AI 초안 항목이 아니라 넣지 않았습니다.

### 부적합 보고서 필수 항목 (로드맵 P2)

> **항목 확정 (2026-11-23, 품질 담당 판단):** 초안 9개에 조치 담당자·조치 기한을 더하고, 영향 범위는 실제 로트 번호로 봅니다. 검사는 표시만 하고 승인을 막지 않습니다. 바꿀 곳은 `NcrCompleteness.ITEMS` 와 그 아래 `check()` 한 곳입니다.

| 키 | 항목 | 통과 조건 | 누가 채우나 |
|---|---|---|---|
| `title` | 제목 | 비어 있지 않음 | AI |
| `phenomenon` | 현상 | 10자 이상 | AI |
| `cause` | 원인 | 추정 원인 또는 확정 원인이 10자 이상 | AI·사람 |
| `causeCode` | 원인 코드 | `UNKNOWN` 이 아닌 코드 | AI |
| `evidence` | 근거 | 숫자(측정값)를 하나 이상 포함 | AI |
| `recommendedAction` | 권장 조치 | 10자 이상 | AI |
| `relatedSensors` | 관련 센서 | 하나 이상 | AI |
| `defectType` | 불량 유형 | 비어 있지 않음 | AI |
| `scope` | 영향 범위 | 영향 로트(`ncr.affected_lots`) 1개 이상 | 자동 (사람이 고칠 수 있음) |
| `actionOwner` | 담당자 | 조치 담당자 지정 | 사람 |
| `actionDueDate` | 조치 기한 | 조치 기한 지정 | 사람 |

**로트 번호 흐름:** 시뮬레이터가 shot 마다 `lotNo` 를 보냅니다(`L{실행 시작일}-{설비}-{순번}`, `simulation.lot_size` 기본 250 shot 마다 바뀜, 난수를 쓰지 않아 정답 재현에 영향 없음) → 브리지·SPC 를 거쳐 `process_shot.lot_no` 에 저장(`22_ncr_owner_due_lot.sql`) → 에이전트가 초안을 만들 때 **같은 설비에서 첫 경보 shot 부터 분석 기준 shot 까지 생산된 로트**를 `affected_lots` 에 채웁니다. 같은 원인의 초안에 합쳐지면 로트 목록도 합칩니다. 로트 번호가 없는 데이터(예전 시뮬레이터·SECOM 재생)는 비어 있어 "영향 범위 빠짐"으로 보입니다.

- 부적합 상세(`GET /api/qms/ncrs/{ncrNo}`)에 `completeness`(충족 수/전체, 빠진 항목, 항목별 이유)가 붙고, 화면 상단 정보에 "필수 항목 9/11 · 빠짐: 담당자, 조치 기한"처럼 보입니다.
- 담당자·기한·영향 로트는 검토 화면의 **조치 지정** 칸에서 정합니다(`PUT /api/qms/ncrs/{ncrNo}/assignment`, 초안·승인 상태에서 가능, 빈 값은 지움, 이력에 남음). 이 항목은 사람이 정하는 값이라 AI 초안 수정률(P3)에는 세지 않습니다.
- 집계 `GET /api/qms/ncrs/completeness`: AI 가 만든 보고서(`created_by='AGENT'`) 전체의 항목별 충족률(`items.*.passRate`), 모든 항목을 채운 비율(`completeRate`), 평균 충족률(`avgRate`).
- 승인을 막지는 않습니다. 사람이 빠진 항목을 보고 고치거나, 알고도 승인할 수 있게 표시만 합니다.

### 원인 평가 지표 (로드맵 E5)

정답 진단 여부만으로는 "거의 맞았는지", "근거를 지어냈는지"를 알 수 없어 네 가지를 함께 봅니다. `evaluate_agent.py` 요약(`summary.md`)과 A/B 비교표에 자동으로 붙습니다. 계산은 `scripts/cause_metrics.py`. **E3 재평가(2026-11-24) 첫 수치: Top-3 적중 100%/100%, 근거 수치 일치율 94%(416개), 인용 사례 실재율 100%(19건), 보류 0건** ([summary](../eval/results/20261124-1440_0467ab7-dirty_base-e3/summary.md)).

| 지표 | 계산 | 왜 보나 |
|---|---|---|
| Top-3 적중 (첫·마지막 판단) | 정답 원인이 `candidateCauses` 앞 3개 안에 있는 사례 비율. 후보가 없으면 `causeCode` 하나 | 1순위는 틀려도 후보에 정답이 있으면 검토자가 빨리 고를 수 있음 |
| 근거 수치 일치율 | 근거에 적힌 수치 중 도구 결과와 맞은 비율 (검증 에이전트 규칙 6 대조 결과 `numberClaims`·`numberVerified`) | 숫자를 지어내는지 |
| 인용 사례 실재율 | `similarCases` 번호 중 DB 에 있는 번호 비율 | 과거 사례 번호를 지어내는지 |
| 보류 적절성 | 판단 보류(F2)된 단계 중 그 단계의 원인이 정답이 아니었던 비율 | 보류가 틀린 결론을 막았는지, 맞는 결론을 붙잡아 두었는지 |

- 출력 형식에 `candidateCauses`(가능성 높은 순 원인 코드 최대 3개)를 추가했습니다. 프롬프트 본문이 바뀌어 `promptVersion` 해시가 달라졌습니다(파일 이름은 analysis-v1 유지, E3 재평가가 이 버전의 기준선).
- 보류 적절성은 보류가 "필요했는데 안 한" 경우(틀린 초안)를 세지 않습니다. 그건 기존 "잘못된 초안" 수로 봅니다.

### 작성 단계 정리 (로드맵 A3)

작성 방식 기본값은 `analysis-text`(분석 문장 그대로)이고, 로컬 소형 LLM 작성(`local`)은 **실험 기능**으로 둡니다(README "실험 기능" 절). 로컬 모델은 문장을 다듬다 수치를 바꿀 위험이 있어, 쓴 문장의 수치를 넘겨준 자료(근거·원시값·정비 기록)와 대조합니다(검증 에이전트 규칙 6과 같은 `EvidenceNumbers`).

- 자료에 없는 수치가 하나라도 있으면 초안에 쓰지 않고 근거 표 초안으로 대신합니다(`report.mode = TEMPLATE_NUMBER_GUARD`, `fallbackReason` 에 그 수치).
- **수치 변조율** = `numberUnsupported` 합 / `numberClaims` 합. 평가 단계 기록(`writerNumberClaims`·`writerNumberUnsupported`)에 남으므로, 맥에서 Ollama 를 켜고 `QG_AGENT_WRITER_MODE=local` 로 평가를 돌리면 잴 수 있습니다. 아직 측정 전입니다.

### 에이전트 전달 방식 비교 (로드맵 A2)

`./gradlew transportBench` (먼저 `docker compose up -d kafka kafka-init`): LLM 을 즉시 답하는 가짜로 바꾸고 사건 200건을 direct 와 Kafka 로 각각 돌려 **전달 비용만** 잽니다. 결과는 [eval/transport_report.md](../eval/transport_report.md).

- 클라우드 컨테이너(Linux amd64, CPU 4개) 1회 측정: direct P50 0.43 ms, Kafka P50 47.9 ms / P95 56.6 ms. 사건당 약 48 ms 를 더하지만 분석 1단계(LLM, 평균 40초 이상)에 비하면 0.1% 수준입니다. 맥에서 다시 재면 파일이 덮어써집니다.
- **판단 (2026-11-23, 결정 C)**: Kafka 를 기본값으로 유지하고, 재시작 복구를 따로 만들었습니다. 복구는 전달 방식과 무관하게 **DB 사건 기록**(`agent_incident.checkpoint_json`)으로 합니다. 앱이 다시 켜지면 끝나지 않은 사건을 되살려 멈춘 단계부터 이어 가고, 이미 끝난 분석·검증·작성은 다시 하지 않습니다(LLM 재호출 없음). 상태 기계 시험은 `IncidentRecoveryTest`, DB 왕복은 컨테이너 시험. 자세한 이유는 [ADR-016](decisions/ADR-016-multi-agent-pipeline.md) 3단계.

### ML 원인 분류 기준선과 LLM 비교 (2026-11-23)

"원인 분석을 LLM 대신 머신러닝으로 하면 어떤가"를 재기 위해, 에이전트와 같은 경보를 랜덤 포레스트로 분류했습니다. `./scripts/ml_baseline.sh` (LLM·DB·Docker 없이 약 1분) → [eval/ml_cause_report.md](../eval/ml_cause_report.md).

- 방법: 시뮬레이터 seed 30개로 학습, 운영과 같은 `SpcEngine` 경보(`./gradlew alarmExport`)마다 **경보 시점까지의 데이터만**으로 특징 66개(센서별 z·기울기·흔들림, 불량률·유형, 경보 규칙). 설비 이름·shot 번호는 넣지 않음
- 같은 시나리오 다른 잡음(seed 1~5): 경보 정확도 0.998, 고장 사례 20/20 을 **첫 경보에서** 맞힘, 단발성 경보 5/5
- 고장을 다른 설비·시점으로 옮긴 시나리오: 경보 정확도 0.996, 사례 20/20 (위치를 외운 것이 아님)
- 판단 1번 약 20 ms, API 비용 0 (에이전트 분석 1단계 평균 62초, E3 재평가)
- **처음 보는 고장**: 원인 하나를 학습에서 빼면 그 고장 20사례 모두 처음 5경보 내내 "단발성 경보(관찰)"로 분류 → 고장을 놓칩니다. '모름'도 내지 않았습니다. 에이전트는 원인 라벨 학습 없이, 과거 사례·정비 이력을 숨긴 조건에서 25/25
- 결론: 정해진 원인 맞히기는 ML 이 빠르고 싸며 이 합성 데이터에서는 정확합니다(같은 시뮬레이터 규칙에서 나온 데이터라 쉬운 문제). 대신 학습한 원인만 낼 수 있고, 근거 문장·조치를 쓰지 못합니다. 그래서 LLM 을 원인 분석·작성에 두는 지금 구조를 유지하고, ML 은 "후보 원인과 확률을 즉시 주는 도구"나 "학습된 원인이 확실할 때 LLM 호출 줄이기"의 후보로 남깁니다(뒤의 '실험 기능' 절에서 두 번째를 기본 꺼짐으로 구현)

### ML 먼저, 애매하면 LLM — 실험 기능 (2026-11-23)

위 비교 뒤 "ML 로 먼저 보고 못 찾은 것만 LLM 에 맡기면?"을 실험 기능으로 만들었습니다. **기본 꺼짐**입니다. `./scripts/ml_cascade.sh` → [eval/ml_cascade_report.md](../eval/ml_cascade_report.md).

- 규칙: ML 이 **학습한 고장 원인**(히터·냉각·체크 링·압력 센서)을 확률 0.9 이상으로 고를 때만 LLM 을 건너뜁니다. **단발성(NOISE)은 ML 이 확신해도 LLM 으로** 넘깁니다(학습하지 않은 고장이 단발성으로 들어가기 때문). 확률이 낮아도 LLM 으로 넘깁니다
- 건너뛸 때도 조회 도구(SPC 요약·센서 추이·불량 요약)를 실제로 불러 그 값만 근거에 쓰고, 검증 에이전트와 사람 승인을 그대로 거칩니다. 검증이 되돌리면 두 번째 시도는 LLM 입니다
- 경보 단위(기준 0.9): LLM 을 건너뛴 경보 93% (같은 시나리오) · 95% (고장 배치 변경), **건너뛴 경보 중 오답 0**
- 고장 사례의 첫 분석: 같은 시나리오 20사례 중 17사례를 ML 이 정답으로 끝냄, 3사례는 LLM 이 분석. ML 오답으로 끝난 사례 0
- 처음 보는 고장(원인 하나를 학습에서 뺌): 98경보 모두 LLM 으로 넘어감, **LLM 없이 오답 0** (기준 0.7 로 낮춰도 0)
- 앱: `MlTriage`(qg.agent.ml-triage.mode = off / shadow / skip). 파이썬에서 학습한 랜덤 포레스트를 JSON 으로 내보내 자바가 직접 계산합니다(파이썬 서버 없음). 같은 seed 42 경보로 **특징 66개와 확률이 scikit-learn 과 같은지** 단위 시험(`CauseFeaturesParityTest`)으로, DB 에 넣은 shot 으로도 같은 원인이 나오고 **LLM 없이 만든 결과가 검증 에이전트를 통과하는지** 컨테이너 시험으로 확인했습니다
- 한계: 시뮬레이터 경보는 대부분 학습한 고장이라 호출 감소율이 높게 나옵니다. 실제 공장은 단발성·처음 보는 경보 비율이 더 높아 감소율이 낮을 것입니다. 시뮬레이터로 학습한 모델이라 실제 설비에는 승인된 NCR 이력으로 다시 학습해야 합니다. 그래서 운영 순서는 `shadow`(기록만)로 실제 경보의 일치율을 본 뒤 `skip` 을 켜는 것입니다

#### 학습에 없는 새 고장을 섞은 무작위 시나리오 (2026-11-23)

"ML 이 학습한 적 없는 고장이면?"을 더 현실적으로 보려고, 시뮬레이터에 **아는 고장과 일부만 닮은 새 고장 3종**(원료 수분 과다, 노즐 막힘, 금형 파팅면 마모)을 넣고 시점·길이·세기를 무작위로 섞었습니다. `./scripts/ml_novel.sh` → [eval/ml_novel_report.md](../eval/ml_novel_report.md).

- 기준 확률 0.9: 새 고장 경보 비율 17% → LLM 생략 76%, 28% → 63%, 50% → 43%. **새 고장을 LLM 없이 틀린 원인으로 처리한 경보 0**, 아는 고장끼리 혼동해 LLM 없이 틀린 경보도 0 (낯선 경보 검사 전에는 1건)
- ML 은 새 고장을 자주 비슷한 아는 고장으로 1순위에 올렸습니다(노즐 막힘 경보의 81% 를 체크 링 마모 등으로). 다만 확률이 낮아(최고 0.64) 모두 LLM 으로 넘어갔습니다. 기준을 0.5 로 낮추면 확률만으로는 새 고장 오답이 생깁니다(15건)
- **낯선 경보 검사**(아래 보완 1): 이렇게 아는 고장으로 1순위에 오른 새 고장 경보의 95%(209/221)를 확률과 관계없이 잡습니다. 기준 0.5 에서도 새 고장 오답 0. 대가는 정상 생략의 약 1% 감소
- 아는 고장도 세기를 바꾸면 첫 경보를 ML 이 끝내는 비율이 낮아집니다(체크 링 7/17). 대신 LLM 으로 넘어갔고 ML 오답은 0
- 결론: 생략률은 '경보 중 아는 고장 비율'로 정해져 시뮬레이터로는 정할 수 없습니다. 실제 비율은 운영 중 `shadow` 로 잽니다

#### 보완: 낯선 경보 검사·판단 기록·표본 점검 (2026-11-23)

1. **낯선 경보 검사** (`qg.agent.ml-triage.novelty-check`, 기본 켬): ML 이 고른 원인으로 분류된 학습 경보들의 특징 평균·표준편차를 모델 파일에 함께 넣고, 새 경보의 표준화 거리가 그 원인 학습 경보 거리의 99.5 백분위를 넘으면 확률이 높아도 LLM 으로 넘깁니다. 자바 계산이 파이썬과 같은지 `CauseFeaturesParityTest` 로 확인
2. **판단 기록과 일치율** (`agent_ml_judgment`, 24_ml_triage.sql): 사건마다 ML 원인·확률·낯선 정도·경로(SHADOW/SKIPPED/AUDIT/LLM_NOISE/LLM_LOW/LLM_UNFAMILIAR)·LLM 원인을 남깁니다. `GET /api/agent/ml-triage/stats?days=7` 이 "건너뛰었을 사건에서 LLM 과 같은 비율(wouldSkipAgreement)", 사람이 승인한 원인과의 일치율, 불일치 예시를 돌려줍니다. 운영 순서: `shadow` 로 이 값을 모은 뒤 `skip`
3. **표본 점검** (`qg.agent.ml-triage.audit-rate`, 기본 0.1): `skip` 모드에서 건너뛸 수 있는 사건 중 10% 는 LLM 이 분석하고(결과도 LLM 것을 씀) ML 답과 함께 기록합니다. 사건 번호로 정해 재시작 복구 뒤에도 같은 경로입니다. skip 을 켠 뒤에도 일치율을 계속 볼 수 있습니다

### 분석 시간 개선과 ML 먼저 켜기 (2026-11-24, E3 다음)

E3 재평가에서 분석 1회 평균 62.2초(43~81초, 19단계 중 11단계가 1분 초과)로 이전보다 느려졌습니다. results.json 의 도구 기록을 보면 마지막 도구 호출이 평균 43.8초, 그 뒤 답 작성이 18.4초였고 단계당 도구 호출은 9.3회였습니다. 느려진 주된 이유는 두 가지입니다. 하나는 모델이 질의만 바꿔 `searchSop` 를 연달아 3번 부른 것처럼 **도구 왕복이 많은 것**(왕복마다 3~4초)이고, 다른 하나는 왕복마다 앞의 결과를 모두 다시 보내 마지막 호출 입력이 **5만~7.6만 토큰**까지 커진 것입니다.

바꾼 점:
1. **SOP 검색은 분석당 1번**(`SopTools`): 두 번째 호출부터는 색인을 보지 않고 "앞 결과(SOP-…)를 쓰고 결론을 내라"는 한 줄만 돌려줍니다. 이 호출은 도구 호출 상한에도 세지 않고, LLM 재시도 때는 처음부터 다시 셉니다. 도구 설명에도 "분석당 한 번, 원인 후보를 정한 뒤 한 질의로"를 적었습니다. 시스템 프롬프트는 바꾸지 않았으므로 프롬프트 버전(analysis-v1@d54b8a16)은 그대로입니다.
2. **도구 결과 줄이기**(`QualityTools`): 추이(`getSensorTrend`)는 모든 행에 반복되던 규격(lsl/target/usl/unit)을 첫 행에만, 구간 시작 시각은 첫 행과 마지막 행에만 둡니다. 구간은 최대 15개(구간 크기를 자동으로 키움), 조회는 최대 500 shot입니다. 권장 인자 300/20·60/5 는 그대로입니다. 유사 사례(`findSimilarNcr`)는 score 에 이미 합쳐진 세부 점수(sensor_match·defect_match·same_equipment)와 빈 의미 유사도를 빼고, 현상·근거·조치 글은 180자까지만 줍니다. 원인(root_cause)·원인 코드·제목·수치는 그대로입니다. 검증 에이전트의 수치 대조도 줄인 뒤의 값(모델이 실제로 본 값)으로 모읍니다.
3. **ML 먼저 켜기**: `qg.agent.ml-triage.mode` 기본값을 `skip` 으로 바꿨습니다. 학습한 고장 원인이고 확률이 0.9 이상이며 낯선 경보가 아닐 때만 LLM 을 건너뜁니다. 단발성(NOISE)은 항상 LLM 이 보고, 건너뛸 수 있는 사건의 10% 는 표본 점검으로 LLM 도 분석해 비교 기록합니다. 끄려면 `QG_AGENT_ML_TRIAGE_MODE=off`.

재측정 방법: 같은 E3 명령으로 다시 돌립니다. **LLM 분석만의 시간**을 E3(62.2초)와 비교하려면 `QG_AGENT_ML_TRIAGE_MODE=off` 로 한 번 돌리고, **ML 을 켠 전체 시스템**은 기본값으로 한 번 더 돌린 뒤 `GET /api/agent/ml-triage/stats` 로 건너뛴 비율과 일치율을 봅니다. 도구 결과 모양이 바뀌었으므로 이 측정이 새 기준선입니다.
