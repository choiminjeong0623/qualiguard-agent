# 05. 한계와 보완할 점 — 면접관 관점의 반박 10가지

면접에서 나올 만한 반박 10가지를 코드와 설정으로 직접 확인해 정리했습니다. 항목마다 **현재 상태**(코드가 실제로 하는 일), **한계**, **보완할 점**을 적고, 보완할 점에는 우선순위를 붙였습니다.

- 우선순위 기준: **높음** = 운영 전에 반드시 필요, **중간** = 규모가 커지거나 실데이터를 붙일 때 필요, **낮음** = 있으면 좋음
- 이 문서는 코드 동작을 바꾸지 않습니다. 확인한 파일 위치를 함께 적었습니다.

## 한눈에 보기

| # | 반박 | 한 줄 답 | 우선순위 |
|---|---|---|---|
| 1 | Kafka 내구성 | 로컬은 브로커 1대·복제 1이라 `acks=all`이 사실상 `acks=1`. 운영 전제(RF 3, min ISR 2)는 미검증 | 높음 |
| 2 | MQTT 유실 방지 범위 | 보장 구간은 브로커 → 브리지 → Kafka. 브로커 큐 상한 1,000건 기본값, 설비 쪽 디스크 버퍼 없음 | 높음 |
| 3 | exactly-once 경계 | Kafka Streams 안에서만. DB는 멱등 INSERT로 "결과적으로 한 번", LLM 호출은 범위 밖 | 중간 |
| 4 | Kafka Connect 대신 직접 브리지 | Connect도 DLQ·변환 있음. 직접 만든 이유는 "Kafka 기록 확인 뒤 MQTT ack" 순서 제어. Connect는 정식 비교하지 않음 | 중간 |
| 5 | 심각도 규칙 | 경보 종류만 봄. 안전 신호·상관 센서 중복·CTQ·고객 등급 미반영 | 중간 |
| 6 | 에이전트 처리량 | 5초마다 1사건, 오래된 순. 심각도 우선 처리 없음, 자동 분석 기본 꺼짐 | 중간 |
| 7 | 중복 제거 캐시 10만 건 | 크기 근거 문서 없음, 재시작 시 소실, 여러 대면 무력 (하류 DB 고유 키가 최종 방어) | 중간 |
| 8 | LLM 환각·MCP 보안 | 검증 에이전트가 사례 실재·조사 여부·불량률은 대조하지만 수치 값 자체는 대조 안 함. `/mcp` 인증 없음 | 높음 |
| 9 | 합성 데이터만 검증 | 결측·재전송·지연·임시 시리얼은 흉내 냈지만 실데이터 미검증, 시리얼 연결·늦은 shot 재판정 미구현 | 높음 |
| 10 | MES/ERP 연계에 Kafka가 꼭 필요한가 | 아니다. 승인은 하루 수십 건. 보장은 아웃박스·재시도·중복 제거가 만든다. 인터페이스(EAI) 서버로 바꾸는 계획 수립 | 중간 |

## 1. Kafka 내구성

**현재 상태**
- `docker-compose.yml`: KRaft 단일 노드. `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1`, `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1`. `kafka-init`이 모든 토픽을 `--partitions 3 --replication-factor 1`로 만듭니다.
- `application.yml` 생산자: `acks: all`, `enable.idempotence: true`.
- 토픽별 `min.insync.replicas` 설정은 없습니다(브로커 기본값 1).

**한계**
- 복제본이 1개라 `acks=all`이 "리더 1대에 기록"과 같습니다. 브로커 디스크가 망가지면 데이터를 잃습니다.
- 운영에서 쓸 RF 3 · `min.insync.replicas=2` · `acks=all` 조합은 문서에 전제로만 있고, 브로커 1대 장애 시 쓰기 계속·2대 장애 시 쓰기 거부(`NotEnoughReplicas`)가 실제로 그렇게 동작하는지 시험한 적이 없습니다.
- 8GB 노트북에서 브로커 3대를 띄우기 어렵다는 것이 단일 노드를 고른 이유입니다(Kafka `mem_limit: 900m`).

**보완할 점**
- (높음) 운영용 compose 또는 설정 프로필을 따로 두어 RF 3, `min.insync.replicas=2`, 내부 토픽(오프셋·트랜잭션 로그) RF 3 / min ISR 2를 명시
- (중간) 브로커 3대 구성에서 한 대를 멈추고 브리지·Streams·DB 적재가 계속되는지, 두 대를 멈추면 브리지가 ack를 보류하는지 장애 시험 1회
- (낮음) 토픽 생성 스크립트에 RF·min ISR을 변수로 받아 로컬/운영을 한 스크립트로

## 2. MQTT 유실 방지 범위

**현재 상태** (`MqttTelemetrySubscriber`, `TelemetryBridgeHandler`, `infra/mosquitto/mosquitto.conf`)
- 브리지: QoS 1, 고정 client-id `qg-bridge` + 지속 세션(`cleanStart=false`, 세션 만료 3,600초), 수동 ack. Kafka 기록 성공을 5초 안에 확인한 메시지만 ack 하고, 실패하면 ack 하지 않아 재접속 때 다시 받습니다. 수신 상한(receiveMaximum) 100건.
- Mosquitto: `persistence true`, `persistence_location /mosquitto/data/`(도커 볼륨). **`max_queued_messages`와 `autosave_interval`은 설정하지 않아 기본값**(큐 1,000건, 자동 저장 1,800초)입니다.
- 브리지 쪽 Paho 클라이언트는 `MemoryPersistence`(메모리)입니다.
- 설비 쪽(시뮬레이터): 설비마다 paho-mqtt 클라이언트, QoS 1, 자동 재연결(1~30초). PUBACK을 못 받은 메시지는 프로세스 메모리에만 있습니다.

**한계**
- 보장하는 구간은 **브로커 → 브리지 → Kafka**입니다. 그 앞 구간은 보장하지 않습니다.
- 브리지가 꺼진 동안 브로커가 쌓아 두는 메시지는 기본값 1,000건이 상한입니다. 지금 시뮬레이터(설비 2대, 0.5초 간격 = 초당 4건)로는 **약 4분** 만에 차고, 넘친 QoS 1 메시지는 버려집니다. 실제 30초 사이클 2대면 약 4시간입니다.
- Mosquitto는 메모리의 큐를 30분마다(또는 정상 종료 때) 디스크에 씁니다. 브로커가 갑자기 죽으면 마지막 저장 이후 쌓인 메시지를 잃을 수 있습니다.
- 설비 → 브로커가 끊기면 설비 쪽은 메모리 큐뿐이라, 설비(또는 게이트웨이) 프로세스가 재시작되면 그동안의 데이터가 사라집니다. 디스크에 쌓았다가 보내는 store-and-forward는 없습니다.

**보완할 점**
- (높음) `mosquitto.conf`에 `max_queued_messages`를 "허용할 브리지 중단 시간 × 초당 메시지 수"로 계산해 설정, `autosave_interval`을 짧게(예: 60초) 또는 `autosave_on_changes`로 조정. 큐가 넘칠 때를 알 수 있게 `$SYS` 지표 감시
- (높음) 설비 앞단 게이트웨이에 디스크 버퍼(store-and-forward)를 두는 구성을 설계 문서에 추가. 실제 PLC·게이트웨이 제품의 기능을 확인해야 하므로 미검증으로 표시
- (중간) 끊김 시험: 브리지를 N분 멈춘 뒤 "보낸 messageId 수 = DB에 저장된 수"를 대조하는 스크립트

## 3. exactly-once 경계

**현재 상태**
- Kafka Streams: `processing.guarantee: exactly_once_v2` — `sensor.raw`를 읽어 SPC 상태(RocksDB) 갱신과 `sensor.clean`·`quality.anomaly` 기록을 하나의 트랜잭션으로 묶습니다.
- DB 적재(`QualityStoreWriter`): `read_committed`로 읽고, `INSERT ... WHERE NOT EXISTS (message_id / anomaly_id)` + 고유 인덱스 + `DuplicateKeyException` 무시로 같은 메시지를 두 번 저장하지 않습니다.
- 브리지 → Kafka는 멱등 생산자이고, 중복 수신은 메모리 캐시로 거릅니다(7번).
- 에이전트 이벤트(`agent.*` 토픽)와 LLM 호출은 일반 Kafka 리스너로 처리합니다.

**한계**
- exactly-once는 **Kafka 안(Streams 읽기 → 상태 → 쓰기)** 에만 해당합니다. DB 적재는 "최소 한 번 전달 + 멱등 저장"이라 결과적으로 한 번이지, 트랜잭션으로 묶인 것은 아닙니다.
- LLM 호출은 범위 밖입니다. 분석 중 앱이 죽어 이벤트가 다시 오면 LLM을 다시 부릅니다(비용 중복, 결과가 달라질 수 있음).
- 브리지의 "Kafka 기록 성공 → MQTT ack 실패" 사이에서는 같은 메시지가 Kafka에 두 번 들어갈 수 있고, 이것도 DB 멱등으로만 막습니다.

**보완할 점**
- (중간) 면접·문서에서 용어를 "Kafka 구간 exactly-once, 전체는 at-least-once + 멱등"으로 통일
- (중간) 에이전트 분석에 사건 ID 기준 멱등 키를 두어, 같은 사건이 다시 오면 저장된 결과를 재사용하고 LLM을 다시 부르지 않기
- (낮음) DB 적재까지 트랜잭션으로 묶어야 한다면 오프셋을 DB에 함께 저장하는 방식 검토(지금은 필요 없음)

## 4. Kafka Connect 대신 직접 만든 브리지

**현재 상태**
- MQTT → Kafka는 앱 안의 `MqttTelemetrySubscriber` + `TelemetryBridgeHandler`가 맡습니다. 형식 검증 실패는 `quality.dlq` 토픽(사유를 헤더에)으로, 결측 항목은 지표로 셉니다.
- ADR-004는 **Spring Integration MQTT 어댑터 대 Paho 직접 사용**을 비교한 기록입니다. 어댑터가 지속 세션 재접속 때 연결 완료 콜백 안에서 구독 완료를 기다려 교착 상태가 생겼고(장애 분석 02), 그래서 Paho를 직접 씁니다.
- **Kafka Connect는 ADR에서 정식으로 비교하지 않았습니다.**

**한계**
- "DLQ·검증 때문에 직접 만들었다"는 답은 약합니다. Kafka Connect도 SMT(단일 메시지 변환)와 `errors.tolerance=all` + `errors.deadletterqueue.topic.name`으로 DLQ를 지원합니다.
- 직접 만든 진짜 이유는 두 가지입니다. ① **Kafka 기록을 확인한 뒤에만 MQTT ack** 하는 순서를 코드로 직접 쥐고 싶었고, ② MQTT 클라이언트를 바꿔 끼운 경험(Spring Integration 교착)에서 재접속·ack 동작을 직접 통제할 필요를 느꼈습니다. MQTT 소스 커넥터가 이 순서를 보장하는지는 확인하지 않았습니다.
- 직접 만든 대가: 확장(태스크 분산), 오프셋·재시작 관리, 운영 도구(REST로 상태 보기)를 Connect가 주는 만큼 갖추지 못했습니다. 브리지는 앱 한 대에 붙어 있습니다.

**보완할 점**
- (중간) ADR에 "Kafka Connect MQTT 소스 커넥터"를 선택지로 추가해, 커넥터별 ack 시점·지속 세션 지원·라이선스를 확인하고 비교 결과를 남기기
- (낮음) 설비 수가 늘면 브리지를 앱에서 떼어 별도 프로세스(또는 Connect)로 옮기는 기준(초당 메시지 수, 설비 수) 정하기

## 5. 심각도 규칙

**현재 상태** (`TriageAgent.classify`)
- 경보 규칙만 보고 정합니다: `P_CHART` → HIGH(제품 영향), `XBAR` → MEDIUM(공정 이동), `S_CHART` → MEDIUM(산포 증가), 그 밖(개별값 이탈) → LOW.
- 검사 결과(`inspection`)를 뺀 센서가 2개 이상 함께 경보를 내면 한 단계 올립니다(LOW → MEDIUM, MEDIUM → HIGH. 이미 HIGH면 그대로).
- 심각도는 사건 표(`IncidentStore`)와 화면 표시에만 쓰이고, 처리 순서나 분석 방식에는 쓰이지 않습니다(6번).

**한계**
- 안전 위험 신호(예: 형체력 이상, 비상 정지, 과열)를 따로 보지 않습니다. 안전 관련은 경보 종류와 관계없이 최상위여야 합니다.
- 서로 강하게 연관된 센서(예: 금형 온도와 실린더 온도는 같은 열 문제에서 함께 움직임)가 같이 울리면 "여러 센서"로 세어 한 단계 올라갑니다. 원인 하나를 두 번 센 셈입니다.
- 제품의 CTQ(핵심 품질 특성) 여부, 고객 등급(자동차 OEM 등), 출하 임박 여부를 반영하지 않습니다.

**보완할 점**
- (중간) 센서에 그룹(열·압력·속도 등)을 두고, 같은 그룹 센서는 하나로 세기
- (중간) 설비·품번별 CTQ·고객 등급 표를 두고 심각도 가중
- (높음, 운영 시) 안전 신호 목록을 따로 정의하고 규칙보다 먼저 최상위로 분류. 지금 시뮬레이터에는 안전 신호가 없으므로 실제 설비 정보가 필요

## 6. 에이전트 처리량

**현재 상태** (`AgentScheduler`, `IncidentAnalyzer.nextSeed`, `application.yml`)
- `qg.agent.auto-enabled: false`가 기본값입니다. 평가·시연은 API로 수동 실행합니다.
- 켜면 5초(`poll-ms: 5000`, fixedDelay)마다 DB를 보고, **진행 중인 사건이 없을 때만** 사건 1개를 시작합니다. LLM 호출을 한 번에 하나로 묶은 것은 8GB 메모리와 비용 상한 때문입니다.
- 다음 사건은 `status = 'NEW'`인 경보 중 **가장 오래된 것**(`ORDER BY detected_at, anomaly_id`)입니다. 실패가 2번 쌓인 경보는 건너뜁니다.
- 경보 하나가 아니라 사건 하나를 처리합니다: 같은 설비의 100 shot·30분 안 경보를 한 사건으로 묶으므로, 경보가 몰려도 사건 수는 그보다 적습니다.

**한계**
- 심각도 우선 처리가 없습니다. 심각도는 시작점을 고른 **뒤에** 정해지므로, 오래된 LOW 사건이 새 HIGH 사건보다 먼저 처리됩니다.
- 분석 1건 평균 44~49초라, 서로 다른 설비에서 사건이 시간당 약 70건 넘게 생기면 백로그가 쌓입니다. 백로그 크기를 보는 지표도 없습니다.
- 자동 분석이 기본 꺼짐이라, 켜는 것을 잊으면 경보가 쌓이기만 합니다.

**보완할 점**
- (중간) 시작점을 고르기 전에 경보 규칙으로 대략의 심각도를 매겨 `ORDER BY 심각도, detected_at`으로 처리(같은 규칙을 SQL에서 재사용)
- (중간) 미처리 경보 수·가장 오래된 대기 시간을 지표로 내보내고 임계값 알림
- (낮음) 비용 한도 안에서 동시 처리 수를 설정값으로(로컬 1, 운영 N)

## 7. 중복 제거 캐시 10만 건

**현재 상태** (`MessageIdDeduplicator`, `qg.bridge.dedup-cache-size: 100000`)
- 최근 messageId 10만 개를 메모리(`LinkedHashMap`, 넣은 순서대로 오래된 것부터 버림)에 둡니다. Kafka 기록에 성공한 뒤에만 기억합니다.
- 클래스 주석에 "재시작하면 기록이 사라지고, 최종 방어선은 하류 DB의 messageId 멱등 처리"라고 적혀 있습니다.

**한계**
- **10만이라는 크기의 근거를 적은 문서가 없습니다.** 아키텍처 문서·docs/03에는 "최근 10만 건"이라는 값만 있습니다. 참고로 지금 시뮬레이터(초당 4건)로 약 7시간, 실제 30초 사이클 2대면 약 17일 분량입니다. QoS 1 재전송은 보통 수초~수분 안에 오므로 크기 자체는 넉넉한 편입니다.
- 재시작하면 비어서, 재시작 직후의 재전송은 Kafka에 중복으로 들어갑니다(DB에서 걸러짐).
- 앱을 여러 대로 늘리면 인스턴스마다 따로 기억해 사실상 무력해집니다. 이것이 docs/03의 Redis 도입 조건과 같은 이야기입니다.

**보완할 점**
- (중간) 크기 근거를 "최대 재전송 지연 × 초당 메시지 수 × 여유 배수"로 계산해 설정 주석과 문서에 남기기
- (중간) 여러 대 구성 시 Redis `SET messageId NX EX <초>` 또는 Kafka 쪽 멱등 처리로 대체 ([docs/03 5절](03-future-local-llm-and-device-security.md))
- (낮음) 중복 지표(`qg.bridge.messages{result=duplicate}`)와 DB 중복 지표(`qg.store.records{result=duplicate}`)를 나란히 보는 대시보드

## 8. LLM 도구 근거 수집과 환각, MCP 보안

**현재 상태**
- 원인 분석 에이전트는 `QualityTools`의 `@Tool` 5개로 데이터를 조회하고, 기준 시점은 모델이 바꿀 수 없게 도구 인자에서 숨겼습니다(ADR-007, ADR-013).
- 검증 에이전트(`VerifierAgent`, 규칙 기반)가 결론을 데이터와 대조합니다:
  - 결론(초안·센서 점검)을 냈다면 센서 추이와 불량 조회 도구를 실제로 불렀는지
  - 근거 문장 중 **숫자가 들어간 것**이 2개 이상인지
  - 인용한 과거 사례 번호가 기준 시점까지 **승인된 NCR로 실재**하는지(DB 조회)
  - "제품 영향 없음" 판단이면 실제 최근 불량률이 크게 오르지 않았는지(DB 조회)
  - 지속성 경보인데 단발성 변동으로 판단하지 않았는지 등 판단·원인 코드 정합성
- `/mcp` 엔드포인트: `SecurityConfig`에서 `anyRequest().permitAll()`에 해당하고 CSRF 검사에서도 뺐습니다. 도구는 모두 조회 전용입니다. ADR-013에 "운영에서는 내부망 제한이나 토큰 인증이 필요"라고 적혀 있습니다.

**한계**
- 근거 수치는 "숫자가 있는지"만 봅니다. 근거에 적힌 **값이 도구가 돌려준 값과 같은지는 대조하지 않습니다.** 모델이 그럴듯한 숫자를 지어내면 통과할 수 있습니다.
- 검증 에이전트의 되돌림은 최대 1회(`verify-max-retries: 1`)입니다. 다시 분석해도 약하면 검증 결과(WEAK)를 기록한 채 다음 단계로 넘어가고, 최종 판단은 사람 승인에 맡깁니다.
- `/mcp`는 **인증이 없습니다.** 조회 전용이라 쓰기 위험은 없지만, 앱에 닿을 수 있는 누구나 공정 데이터·NCR을 읽을 수 있습니다. MCP 클라이언트별 사용자 구분도 없습니다. 같은 이유로 `/api/agent/**`, `/actuator/**`도 열려 있습니다.

**보완할 점**
- (높음) `/mcp`·`/api/agent/**`에 토큰 인증(또는 내부망 제한), 조회 기록(누가 무엇을 봤는지) 남기기
- (중간) 근거 문장의 숫자를 도구 호출 기록(`toolTrace`)의 응답 값과 대조하는 검증 규칙 추가
- (낮음) 근거를 자유 문장 대신 "도구 이름 + 조회 조건 + 값" 구조로 받도록 출력 형식 변경

## 9. 합성 데이터로만 검증

**현재 상태**
- 모든 성과 수치는 시뮬레이터(설비 2대 × 2,000 shot, 고장 4종) 데이터에서 잰 값입니다. 공개 실데이터(SECOM)에는 탐지 규칙만 적용해 봤고, 경보가 과다해 그대로 쓰기 어렵다는 결과를 얻었습니다.
- 멘토링 피드백을 PR #26(ADR-017)에 반영했습니다: 센서 값 null·연속 결측, 메시지 통째 누락·재전송·지연, 임시·중복·미할당 시리얼을 시뮬레이터로 섞고, 브리지 필수 항목을 `messageId·lineId·equipmentId·ts`로 줄여 나머지 결측은 정상으로 저장합니다. 늦게 온 shot은 `ts` 기준으로 저장만 하고(`arrival_late`), 확정 시리얼 연결 표(`shipment_serial_link`)는 표만 만들었습니다.

**한계**
- 실제 설비 데이터로는 검증하지 않았습니다. 실제 결측 패턴, 센서 잡음, 설비 간 차이, 고장 종류는 시뮬레이터 가정과 다를 수 있습니다.
- PR #26의 남은 일 두 가지가 아직 없습니다.
  - **출하 확정 때 시리얼 연결**: `shipment_serial_link`를 채우는 로직(출하 화면·API, 임시 시리얼이 겹칠 때 사람이 shot을 고르는 절차)
  - **늦게 온 shot 재판정**: 지금은 저장만 하므로, 늦게 온 shot이 이미 지나간 관리도 판정에 반영되지 않습니다.

**보완할 점**
- (높음) 실제 설비(또는 협력사 익명 데이터) 1대분으로 결측률·경보 빈도·오경보율을 먼저 재고, 시뮬레이터 결측 설정을 그 값에 맞추기
- (중간) 늦게 온 shot 재판정 방식 결정: 일정 지연 안에서는 순서를 맞춰 다시 판정, 그 밖은 별도 표시. 재판정 시 경보 중복을 어떻게 막을지 함께 정하기
- (중간) 출하 확정 시 시리얼 연결 API와 임시 시리얼 충돌 처리 화면
- (낮음) 고장 시나리오를 4종에서 늘리고, 실데이터에서 본 고장 유형을 우선 추가

## 10. MES/ERP 연계에 Kafka가 꼭 필요한가

**현재 상태**
- 승인 → `integration_outbox`(같은 트랜잭션) → `OutboxPublisher` → Kafka `quality.ncr.approved` → 같은 앱의 `MesErpReceiver`(소비자 그룹 `qg-mes-erp-sim`) → `integration.ncr.ack` → `IntegrationAckListener`(그룹 `qg-qms-ack`).
- Kafka 를 고른 이유는 "센서용 Kafka 가 이미 있어서"였고, 양 때문은 아니었습니다.

**한계**
- NCR 승인은 하루 몇 건~몇십 건이라 Kafka 의 처리량·보관 장점이 거의 쓰이지 않습니다.
- 현장의 MES/ERP 담당자는 EAI·인터페이스 서버와 연계 이력 테이블로 운영하는 데 익숙하고, Kafka 토픽·오프셋은 낯섭니다.
- 가상 MES/ERP 가 QMS 와 같은 앱 안에 있어 "다른 시스템과의 연계"라는 경계가 약합니다.

**보완할 점**
- (중간) 아웃박스는 유지하고 발행 대상만 **인터페이스 서버 REST**로 바꾸기: 지수 백오프 재시도, `Idempotency-Key`, 어댑터 라우팅, `(event_id, 시스템)` 중복 제거, 콜백으로 RECEIVED/PROCESSED/FAILED(seq) → [06. MES/ERP 연계 EAI 계획](06-mes-erp-eai-plan.md), [ADR-018](decisions/ADR-018-mes-erp-eai-interface-server.md)
- 면접 답: "양 때문이 아니라 기존 인프라 재사용으로 Kafka 를 썼다. 한 번만 처리는 아웃박스·재시도·중복 제거가 보장하므로, 양이 적은 MES/ERP 연계는 인터페이스 서버로 바꾸는 것이 더 맞다."
