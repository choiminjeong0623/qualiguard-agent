# ADR-009. QMS 검토 화면: 상태 규칙은 저장 프로시저에, 화면은 jQuery 정적 페이지로

- 상태: 채택
- 날짜: 2026-11-15
- 관련 요구사항: F-08(담당자가 초안을 검토·수정·승인), N-05(AI 판단을 사람이 검증)

## 배경
에이전트가 만든 부적합 초안은 `DRAFT`로만 쌓이고, 사람이 확인해 승인하는 길이 없었습니다. 정해야 할 것은 세 가지였습니다.
1. 상태 규칙(초안에서만 수정·승인·반려, 승인에 필요한 값)을 어디서 지킬지
2. AI 초안을 사람이 어떻게 고쳤는지 어떻게 남길지
3. 화면을 어떤 기술로 만들지

## 결정 1. 쓰기는 저장 프로시저 하나에서 상태 확인·변경·이력을 함께 처리한다
| 선택지 | 장단점 |
|---|---|
| Java 서비스에서 조회 → 확인 → UPDATE | 확인과 변경 사이에 다른 요청이 끼어들 수 있음, 규칙이 화면·API 마다 흩어짐 |
| **프로시저(`usp_UpdateNcrDraft`, `usp_ReviewNcr`)** | `UPDLOCK`으로 잠근 뒤 상태 확인·변경·이력 기록을 한 트랜잭션에서 처리. 규칙 위반은 `THROW 504xx`로 거절 |

- 오류 번호를 HTTP 상태와 맞췄습니다: 50400(입력 부족) → 400, 50404(없음) → 404, 50409(상태가 맞지 않음) → 409.
- [ADR-007](ADR-007-sqlserver-qms-schema.md)의 "조회는 프로시저" 원칙을 쓰기에도 그대로 적용했습니다.

## 결정 2. 승인에는 확정 원인과 원인 코드가 있어야 한다
승인된 부적합은 다음 분석의 유사 사례(지식저장소)가 됩니다 (F-10). 원인이 비어 있거나 `UNKNOWN`·`NOISE`인 사례가 지식저장소에 들어가면 다음 판단을 흐리므로, **승인 조건으로 확정 원인(`root_cause`)과 원인 코드(UNKNOWN·NOISE 제외)를 요구**합니다. 반려에는 사유를 요구합니다.

## 결정 3. 바뀐 항목만 전·후 값과 함께 이력에 남긴다
`ncr_history`에 수정·승인·반려를 모두 남기고, 수정은 실제로 바뀐 항목만 `{"필드": {"before", "after"}}`로 저장합니다. "AI 초안을 사람이 무엇을 고쳤는지"가 쌓이면 에이전트 개선의 근거가 됩니다.

## 결정 4. 화면은 jQuery 정적 페이지 (Kendo UI 는 쓰지 않음)
| 선택지 | 장단점 |
|---|---|
| Kendo UI | 처음 계획한 기술. 표(Grid)는 상용 라이선스가 필요하고, 라이선스 키 없이 쓰면 경고가 뜸 |
| React 등 SPA | 빌드 도구가 하나 더 필요, 8GB 환경에서 개발 서버를 따로 띄워야 함 |
| **jQuery + 정적 HTML (`static/qms/`)** | 앱과 같은 JVM 에서 바로 제공, 빌드 없음. 표는 일반 HTML 표 |

화면 코드(`qms.js`)는 API 호출과 그리기를 나눠 두어, 나중에 Kendo Grid 같은 부품으로 바꾸기 쉽게 했습니다.

## 결과
- 화면: `http://localhost:8080/qms/index.html` — 상태별 목록, 상세(연결된 경보·에이전트 분석 기록·도구 호출 순서), 수정·승인·반려, 검토 이력
- API: `GET/PUT /api/qms/ncrs/{ncrNo}`, `POST .../approve`, `POST .../reject`

## 한계
- **로그인이 없습니다.** 검토자 이름을 요청마다 받아 이력에 남기는 시연용 방식입니다. 실제 운영에서는 사내 인증(SSO)과 권한(작성자·승인자 분리)이 필요합니다.
- 동시에 같은 초안을 고치면 나중 저장이 이깁니다. 상태 규칙은 잠금으로 지키지만, 내용 충돌 알림(버전 비교)은 없습니다.
