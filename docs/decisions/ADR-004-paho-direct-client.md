# ADR-004. MQTT 수신에 Paho 클라이언트를 직접 사용한다

- 상태: 채택 (초기 결정인 "Spring Integration MQTT 어댑터 사용"을 대체)
- 날짜: 2026-11-14

## 배경
MQTT 브로커는 기본적으로 구독자가 없으면 메시지를 버립니다. 브리지가 재배포 등으로 잠시 꺼져도 데이터를 잃지 않도록 **지속 세션**(고정 client-id, cleanStart=false)과 **수동 ack**(Kafka 기록 성공 후에만 확인)를 설계했습니다.

처음에는 엔터프라이즈 통합 패턴(EIP) 프레임워크인 Spring Integration의 MQTT v5 어댑터로 구현했습니다.

## 문제
밀린 메시지가 있는 상태에서 브리지가 재접속하자 `서버에서 응답을 기다리는 중 제한시간 초과 (32000)` 오류로 구독에 실패했습니다. 분석 결과 **교착 상태**였습니다. ([장애 분석 보고서](../troubleshooting/02-mqtt-persistent-session-deadlock.md))

- 어댑터는 "접속 완료" 콜백 안에서 구독을 요청하고 **완료될 때까지 기다립니다.**
- Paho 클라이언트는 수신 메시지 처리와 "구독 완료" 처리를 **같은 콜백 스레드 하나**에서 차례로 합니다.
- 콜백 스레드가 기다리느라 멈춰 있으니 구독 완료 신호를 처리하지 못합니다.

밀린 메시지가 있을 때 재접속하는 것은 지속 세션을 쓰는 이유 그 자체라서, 설정 조정으로는 피할 수 없었습니다.

## 고려한 선택지
| 선택지 | 결과 |
|---|---|
| 지속 세션을 끄기 (cleanStart=true) | 문제는 사라지지만 브리지가 꺼진 동안의 데이터를 잃음 → 요구사항 위반 |
| **Paho 클라이언트 직접 사용, 구독은 비동기 요청** | 지속 세션과 수동 ack를 유지하면서 교착 상태 제거 |

## 결정
`MqttTelemetrySubscriber`에서 Paho MQTT v5 클라이언트를 직접 사용합니다. 접속 완료 콜백에서는 **구독을 요청만 하고 바로 반환**하며, 구독 결과는 비동기 알림으로 받아 로그만 남깁니다.

## 결과
- 함께 보강한 것
  - 수신 상한(receiveMaximum) 100건: 밀린 메시지가 많아도 감당할 만큼씩만 받음
  - 첫 접속 실패 시 5초마다 재시도 (Paho 자동 재접속은 첫 접속 성공 이후에만 동작)
  - 콜백 안의 예외를 모두 처리 (예외가 밖으로 나가면 Paho가 연결을 끊음)
- 메시지 처리 로직(`TelemetryBridgeHandler`)은 MQTT를 몰라도 되게 분리해, "ack 해도 되는지"만 돌려줍니다.
- 이번 결정으로 MQTT 수신에는 Spring Integration을 쓰지 않습니다. 의존성은 이후 다른 연계에 쓸 수 있어 남겨 두었습니다.
