# ADR-021. 현장 수집은 MQTT, 사내 처리는 Kafka — 둘 사이는 직접 만든 브리지로 잇는다

- 상태: 채택 (구현은 2026-11-14 부터 이미 이 구조, 비교 기록은 2026-11-24 작성)
- 날짜: 2026-11-24
- 관련: [ADR-001](ADR-001-shot-level-message.md)(shot 단위 메시지), [ADR-004](ADR-004-paho-direct-client.md)(Paho 직접 사용·지속 세션·수동 ack), [ADR-006](ADR-006-kafka-streams-state.md)(Kafka Streams 상태), [ADR-015](ADR-015-mqtt-device-auth.md)(장비 인증), [ADR-016](ADR-016-multi-agent-pipeline.md)(에이전트 사이 Kafka), [05. 한계 4번](../05-limitations-and-improvements.md)

## 배경
설비(사출성형기)는 shot 마다 공정 값과 검사 결과를 보냅니다. 이 데이터를 받아 실시간으로 SPC 판정을 하고, DB 에 쌓고, 경보를 에이전트에 넘겨야 합니다. 처음부터 "현장은 MQTT, 사내는 Kafka"로 만들었지만, **왜 하나만 쓰지 않았는지**를 비교한 기록이 없었습니다. 면접에서 가장 먼저 나올 질문이라 선택지를 정리해 둡니다.

두 기술은 하는 일이 다릅니다.

| | MQTT (Mosquitto) | Kafka |
|---|---|---|
| 만든 목적 | 작고 불안정한 장비가 브로커에 메시지를 **보내는** 것 | 사내 시스템 사이에서 메시지를 **보관하고 여러 번 읽는** 것 |
| 클라이언트 | 아주 가벼움(PLC·게이트웨이·임베디드에도 라이브러리 있음), 연결 하나 | 무거움(배치·파티션·오프셋 관리), 장비 쪽에 두기 어려움 |
| 연결 끊김 | Keep-alive, 유언(LWT), 지속 세션으로 재접속 뒤 이어 받기 | 클라이언트가 재접속은 하지만 장비 환경을 전제로 만들지 않음 |
| 보관 | 구독자가 받으면 끝. 지속 세션이면 그 구독자 몫만 잠시 보관 | 디스크에 보관 기간만큼 남음(이 프로젝트 72시간), 오프셋으로 다시 읽기 |
| 여러 소비자 | 각자 구독하면 되지만, 늦게 온 소비자는 지난 데이터를 못 받음 | 소비자 그룹마다 따로 읽음. 새 소비자도 처음부터 읽을 수 있음 |
| 순서 | 토픽·연결 단위, 전체 처리 순서 보장 수단은 없음 | 파티션 안에서 보장. key = 설비 ID 로 설비별 순서 유지 |
| 상태 있는 처리 | 없음 | Kafka Streams 상태 저장소 + exactly-once(ADR-006) |
| 접근 제어 | 사용자명·비밀번호·토픽 ACL·TLS(ADR-015) | SASL·ACL(이 프로젝트에서는 사내망이라 미적용) |

## 고려한 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. MQTT 만 | 구성 단순, 장비부터 앱까지 한 가지 | 브리지가 꺼진 동안은 지속 세션이 막아 주지만, **새로 붙는 소비자(DB 적재·재생 평가)는 지난 데이터를 못 읽음**. 설비별 상태를 장애 뒤 복원하고 경보를 한 번만 내는 수단(ADR-006)을 직접 만들어야 함 |
| B. Kafka 만 (장비가 Kafka 에 직접 보냄) | 중간 단계 없음 | 장비·게이트웨이에 Kafka 클라이언트를 올려야 함. 설비마다 Kafka 계정·연결을 관리해야 하고, 공장망의 불안정한 연결을 Kafka 클라이언트가 견디도록 만들어야 함. 실제 현장 장비는 MQTT·OPC UA 를 주로 지원 |
| **C. MQTT + 직접 만든 브리지 + Kafka** | 장비는 가벼운 MQTT 만 알면 됨. 사내는 보관·다시 읽기·설비별 순서·exactly-once 를 Kafka 로 얻음. 브리지에서 형식 검증·중복 제거·DLQ 를 한 번에 처리 | 브리지 하나 더 운영. MQTT ack 와 Kafka 기록 사이에서 중복이 생길 수 있음(아래 결과) |
| D. MQTT + Kafka Connect MQTT 소스 커넥터 + Kafka | 브리지를 직접 만들지 않음. 태스크 분산·오프셋·REST 운영 도구 | **"Kafka 기록 확인 뒤 MQTT ack" 순서를 보장하는지 확인하지 않음**. 커넥터마다 지속 세션 지원·라이선스가 다름. Connect 클러스터를 따로 띄워야 함(8GB 개발 환경에 부담) |

## 결정
**C** 를 택했습니다.

- 장비 → Mosquitto: 토픽 `factory/{라인}/{설비}/telemetry`, QoS 1, 장비별 계정·토픽 ACL(ADR-015), 브로커 persistence 켬
- Mosquitto → 브리지: 고정 client-id `qg-bridge` + 지속 세션(만료 3600초) + **수동 ack**(ADR-004)
- 브리지 → Kafka `sensor.raw`: key = 설비 ID, `acks=all`, 기록 성공을 확인한 뒤에만 MQTT ack. 형식 오류는 `quality.dlq`(사유는 헤더), messageId 최근 10만 건으로 중복 제거
- Kafka 안: `sensor.raw` → SPC(Kafka Streams, exactly-once) → `sensor.clean`·`quality.anomaly` → DB 적재·에이전트(`agent.*`, ADR-016)

## 근거
1. **보관과 다시 읽기가 실제로 쓰입니다.** `sensor.raw` 는 SPC 가, SPC 결과(`sensor.clean`·`quality.anomaly`)는 DB 적재와 에이전트가 각자 읽고, 재생 평가(E3·E4)와 장애 뒤 재처리도 Kafka 에 남은 데이터를 씁니다. MQTT 만으로는 늦게 붙은 소비자가 지난 데이터를 받을 수 없습니다.
2. **설비별 상태를 다루는 처리가 있습니다.** SPC 는 설비마다 기준값·연속 이탈 횟수를 들고 있어야 하고, 재시작 뒤 복원과 경보 한 번만 내기가 필요합니다(ADR-006). Kafka 는 key 로 설비별 순서를, Streams 로 상태 복원과 exactly-once 를 줍니다.
3. **장비 쪽은 가벼워야 합니다.** 장비는 연결이 자주 끊기고 자원이 작습니다. MQTT 는 이 환경을 전제로 만들어졌고, 장비 인증·토픽 ACL 도 브로커 한곳에서 합니다. 실제 공장에서 많이 쓰는 "현장은 MQTT(또는 OPC UA), 사내는 Kafka" 구성과 같습니다.
4. **브리지를 직접 만든 이유**(D 대신 C)는 "Kafka 기록 확인 → MQTT ack" 순서를 코드로 직접 쥐기 위해서입니다. Spring Integration 어댑터에서 재접속 교착을 겪은 뒤(ADR-004) 재접속·ack 동작을 직접 통제할 필요를 느꼈습니다.

## 결과
- 유실 방지 범위: 브리지가 꺼져도 지속 세션이 보관하는 동안(3600초)은 잃지 않습니다. 브로커 자체가 죽으면 persistence 로 디스크에 남긴 것까지만 보장합니다.
- **중복 가능 지점**: Kafka 기록은 성공했는데 MQTT ack 가 실패하면, 브로커가 같은 메시지를 다시 보내 Kafka 에 두 번 들어갈 수 있습니다. 브리지 메모리 중복 제거(10만 건) → SPC 상태의 최근 messageId 200건 → DB 고유 키, 세 겹으로 거릅니다.
- 브리지는 앱 한 대에 붙어 있어 설비가 많아지면 확장 한계가 있습니다. Kafka 는 개발 환경에서 복제 1, 파티션 3 입니다.
- 에이전트 사이 전달도 Kafka 로 하는 것이 맞는지는 ADR-016 3단계에서 따로 측정했습니다(direct P50 0.43 ms 대 Kafka 47.9 ms, LLM 분석 시간의 0.1% 수준 → Kafka 유지 + 재시작 복구).
- MES/ERP 로 보내는 승인 결과는 양이 적어 Kafka 대신 인터페이스 서버로 바꾸는 계획입니다(ADR-018). 즉 Kafka 는 "양이 많고 여러 소비자가 다시 읽는 흐름"에만 씁니다.

## 하지 않은 것
- **선택지 D(Kafka Connect MQTT 소스 커넥터)는 실행해 비교하지 않았습니다.** 커넥터별 ack 시점·지속 세션 지원·라이선스를 확인하는 일은 [05. 한계 4번](../05-limitations-and-improvements.md)의 보완할 점으로 남아 있습니다.
- MQTT 만 쓰는 구성(A)과 처리량·지연을 측정해 비교하지 않았습니다. 이 결정은 측정이 아니라 기능 요구(보관·다시 읽기·상태 복원)로 했습니다.
- 브리지를 앱에서 떼어 낼 기준(초당 메시지 수, 설비 수)은 아직 정하지 않았습니다.
