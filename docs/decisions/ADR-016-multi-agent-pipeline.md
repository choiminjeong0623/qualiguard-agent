# ADR-016. 역할 분리형 멀티 에이전트 — Kafka 이벤트로 잇는다

- 상태: 채택 (2026-11-15). 1단계 검증 에이전트, 2단계 분류·오케스트레이터·보고서 작성·Kafka 연결 구현, 3단계 전달 방식 판단·재시작 복구 (2026-11-23)
- 관련: [ADR-005](ADR-005-spc-detect-llm-reason.md) 탐지는 SPC·판단은 LLM, [ADR-008](ADR-008-agent-design.md) 원인 분석 에이전트

## 배경
지금까지는 원인 분석 에이전트 하나가 사건 묶기 → 조사 → 판단 → 초안 저장을 모두 했습니다. 이 구조에는 두 가지 약점이 있습니다.
1. **자기 검증이 없습니다.** 모델이 도구를 건너뛰거나, 지어낸 사례 번호를 쓰거나, "제품 영향 없음"이라 해 놓고 불량률이 오른 경우를 잡지 못합니다.
2. **단계가 한 함수에 묶여 있습니다.** 어디서 오래 걸리는지, 어디서 실패했는지 따로 보기 어렵고, 보고서 작성만 로컬 모델로 바꾸는 것처럼 단계별로 바꾸기 어렵습니다.

## 결정 (전체 설계)
역할마다 에이전트를 나누고, 넘겨주는 지점마다 Kafka 토픽을 둡니다. 사람 승인은 항상 마지막입니다.

| 에이전트 | 하는 일 | 방식 |
|---|---|---|
| 분류(Triage) | 경보 심각도·유형 판정, 같은 설비 경보를 사건으로 묶음 | 규칙 |
| 원인 분석 | 도구로 근거를 모아 원인 추정 | LLM (Gemini) |
| **검증(Verifier)** | 분석 결과를 데이터와 대조, 약하면 분석으로 되돌림 (횟수 제한) | **규칙** |
| 보고서 작성 | 기밀 데이터가 든 초안 문장 작성 | 로컬 소형 LLM, 실패 시 근거 표 초안 (클라우드로 넘기지 않음) |
| 오케스트레이터 | 사건 상태 관리: 분류 → 분석 → 검증 → 작성 → 사람 승인 | 상태 기계 |

LangGraph 같은 Python 프레임워크 대신 Spring AI + Kafka 로 만듭니다. 이미 데이터 흐름이 Kafka 위에 있고, 8GB 개발 환경에서 런타임을 하나 더 띄우지 않기 위해서입니다.

## 1단계: 검증 에이전트 (구현)
`VerifierAgent` — LLM 을 쓰지 않는 규칙 기반 검증입니다.
- **왜 LLM 이 아닌가**: 분석 1단계가 이미 평균 45~49초라 LLM 검증을 붙이면 1분 목표에서 더 멀어집니다. 또 같은 모델이 자기 답을 다시 읽는 검증은 독립적인 확인이 되기 어렵습니다. 그래서 **모델이 바꿀 수 없는 것**(도구 호출 기록, DB 의 실제 값, 경보 규칙)과 결과를 맞춰 봅니다.
- **규칙은 모두 일반 원칙**입니다. 특정 고장을 맞히기 위한 힌트는 넣지 않습니다.

| 규칙 | 되돌림(FAIL) 조건 |
|---|---|
| 조사 충분성 | 결론(초안·센서 점검)을 냈는데 센서 추이나 불량 조회 도구를 부르지 않음 |
| 근거 수치 | 결론의 근거 중 수치가 담긴 것이 2개 미만 (도구 결과를 받았으면 **도구 결과와 맞는** 수치가 담긴 근거로 센다) |
| 판단·원인 정합 | 초안인데 원인이 UNKNOWN·NOISE / 지속성 경보인데 NOISE / 관찰인데 watchItems 없음 |
| 과거 사례 실재 | 인용한 사례가 기준 시점까지 승인된 사례에 없음 (지어낸 번호·미래 사례) |
| 데이터 대조 | "제품 영향 없음"(센서 점검)인데 불량률 경보가 있거나, 최근 50 shot 불량률이 앞 250 shot 의 2배 이상이면서 5%p 이상 높음 |
| 수치 대조 (2026-11-22 추가) | 결론의 근거에 적힌 수치 중 **절반 넘게** 이번 조사에서 도구가 돌려준 값에 없음. 일부만 어긋나면 WARN 으로 기록 |

**수치 대조의 동작** (`EvidenceNumbers`, `ToolObservations`)
- `QualityTools` 가 DB 결과를 모델에게 돌려줄 때 같은 값(과 조회 인자)을 사건별 바구니 `ToolObservations` 에 넣습니다. 재분석 시도도 같은 바구니를 씁니다(기준 시점이 같아 앞서 본 값도 유효).
- 근거 문장에서 수치를 뽑아(설비·사례 번호, 날짜·시각은 제외) 바구니의 값과 맞춥니다. 일치로 보는 경우는 ① 같은 값(적힌 자릿수의 반올림 오차까지, 224.1 이면 ±0.05) ② 비율을 퍼센트로 적은 값(0.062 → 6.2%) ③ 부호(+/−)나 %p 가 붙은 변화량은 두 관측값의 차이입니다.
- 조회 범위(`shot`·`샷`)와 모델이 계산한 값(`σ`·`배`)은 도구 결과에 그대로 없으므로 대조하지 않습니다.
- 한 개만 어긋나도 되돌리면, 모델이 여러 구간을 직접 평균 내 적은 값 같은 정당한 계산까지 재분석(약 45초)을 부르므로, 절반 넘게 어긋날 때만 되돌리고 나머지는 사람이 보도록 기록합니다.
- 한계: 수치가 맞는지만 볼 뿐 "어느 센서의 값인지"는 확인하지 않습니다(금형 온도 값을 실린더 온도라고 적어도 통과). 문장의 주어와 도구 결과의 칸 이름을 맞추는 것은 향후 과제입니다.

- 되돌릴 때는 지적 문장과 앞선 결과를 붙여 분석 에이전트를 다시 부릅니다. **최대 `verify-max-retries`(기본 1)회**입니다.
- 다시 분석해도 약하면 결과는 그대로 쓰되 `verify_status = WEAK` 로 남기고, 초안이면 근거 끝에 "검증 에이전트: 근거 부족 — …"을 붙여 검토자가 보게 합니다. 판단을 검증 에이전트가 바꾸지는 않습니다(최종 판단은 사람).
- 기록: `agent_analysis.attempts`, `verify_status`, `verify_json`. QMS 화면의 에이전트 분석 기록에 "검증 통과 / 재분석 n회 / 근거 부족" 태그와 지적 내용을 보여 줍니다.

## 2단계: 오케스트레이터와 Kafka 토픽 (구현)
코드: `qms-app/.../agent/pipeline/`

```
경보 ─▶ 분류 ──agent.incident.triaged──▶ 오케스트레이터 ──agent.analysis.requested──▶ 원인 분석(LLM)
                                            ▲  │                                        │
                 agent.analysis.completed ──┘  └──agent.verification.requested──▶ 검증(규칙)
                 agent.verification.completed ◀───────────────────────────────────────┘
          PASS·초안 ──agent.report.requested──▶ 보고서 작성(로컬/근거 표) ──agent.report.completed──▶ 승인 대기
          WEAK·재분석 남음 ──▶ 지적을 붙여 agent.analysis.requested (횟수 제한)
          관찰·센서 점검 ──▶ 종결 / 분석 실패 ──▶ 실패 (경보는 다시 분석 대상)
```

| 상태 | 뜻 |
|---|---|
| TRIAGED → ANALYZING → VERIFYING → (ANALYZING …) → WRITING → **AWAITING_APPROVAL** | 초안: 사람 승인을 기다림 (QMS 화면) |
| … → VERIFYING → CLOSED | 관찰·센서 점검: 초안 없음 |
| … → FAILED | 분석 실패 |

- **분류 에이전트는 규칙**입니다. 경보 규칙의 뜻이 이미 분명해서(P_CHART=제품 영향 HIGH, XBAR=평균 이동 MEDIUM, S_CHART=산포 MEDIUM, INDIVIDUAL=단발 LOW, 여러 센서 동시면 한 단계 위) LLM 을 부를 이유가 없고, 모든 경보에 LLM 을 부르지 않는다는 비용 원칙(N-04)을 지킵니다. 사건 묶기는 기존 규칙(같은 설비·100 shot·30분)을 그대로 씁니다.
- **오케스트레이터는 스스로 판단하지 않습니다.** 상태를 바꾸고 다음 에이전트에게 일을 넘기기만 합니다. 되돌림 횟수 제한도 여기서 지킵니다.
- **보고서 작성 에이전트** (`qg.agent.writer.mode`)
  - `analysis-text`(기본): 분석 에이전트가 쓴 문장 그대로. 평가 결과가 기존과 같도록 기본값으로 둡니다.
  - `local`: Ollama 소형 모델(예: qwen2.5 1.5B 4bit)이 원시 shot 값·정비 기록을 보고 문장을 씁니다. 이 자료는 로컬 모델에만 갑니다.
  - 로컬 모델이 실패하거나 시간을 넘기면 **클라우드로 넘기지 않고** 근거 표 + "사람 작성 필요" 초안으로 대신합니다(`TEMPLATE_FALLBACK`). 작성 기록에 `cloudCalls: 0` 을 남깁니다.
  - 작성 에이전트는 문장만 씁니다. 판단(decision·원인 코드·확신도)은 바꾸지 않습니다.
- **Kafka 전달** (`qg.agent.pipeline.transport=kafka`, 기본)
  - 메시지는 사건 ID + 요약만 담습니다. 무거운 작업 상태(프롬프트·도구 기록)는 한 JVM 안의 사건 저장소에 둡니다. 8GB 환경에서 프로세스를 늘리지 않으면서, 토픽 계약은 나중에 에이전트를 다른 프로세스로 떼어 낼 때 그대로 쓸 수 있게 했습니다.
  - 키 = 사건 ID → 한 사건의 이벤트는 같은 파티션에서 순서대로 처리됩니다. 에이전트마다 소비자 그룹이 따로이고 동시 처리는 1건입니다(LLM 호출을 한 번에 하나로).
  - `direct` 로 바꾸면 Kafka 없이 같은 스레드에서 이어 부릅니다. 단위 시험(`AgentPipelineTest`)이 이 방식으로 상태 기계 전체(되돌림·작성 대체·실패)를 확인합니다.
- **기록**: `agent_incident`(사건 상태), `agent_incident_event`(단계마다 한 줄), `agent_analysis.incident_id`·`pipeline_json`(분류·작성·단계 시간). QMS 화면의 분석 기록에 분류 결과와 단계별 시간이 보입니다.
- **API·스케줄러**: `/api/agent/analyze/*`, `/recheck/*` 는 파이프라인에 사건을 넣고 승인 대기·종결까지 기다려(`wait-seconds`, 기본 600) 같은 형식으로 결과를 돌려줍니다. 자동 분석은 기다리지 않고, 진행 중인 사건이 있으면 새 사건을 넣지 않습니다.

## 3단계: 전달 방식과 재시작 복구 (2026-11-23)

> 초안입니다. 판단은 민정이 했고(결정 C), 문장은 민정이 고쳐 확정합니다.

**측정** (로드맵 A2, `./gradlew transportBench`, [eval/transport_report.md](../../eval/transport_report.md)): LLM 을 즉시 답하는 가짜로 바꾸고 사건 200건을 돌리면 direct P50 0.43 ms, Kafka P50 47.9 ms 입니다. Kafka 는 사건당 약 48 ms 를 더하지만, 분석 1단계(LLM 평균 40초 이상)의 0.1% 수준이라 사용자가 느낄 차이는 없습니다.

**측정이 보여 준 문제**: 그때까지 사건 상태는 메모리에만 있어서, Kafka 를 써도 앱이 재시작하면 토픽에 남은 이벤트가 "모르는 사건"으로 버려졌습니다. Kafka 를 고른 이유 중 하나였던 "장애가 나도 이어 간다"가 실제로는 성립하지 않았습니다.

**검토한 선택지**
| | 선택 | 장점 | 단점 |
|---|---|---|---|
| A | direct 를 기본으로 | 단순, 빠름 | 에이전트를 다른 프로세스로 떼어 낼 길이 없어짐. 복구 문제는 그대로 |
| B | Kafka 유지, 한계만 기록 | 작업 없음 | 설명과 실제 동작이 어긋난 채로 남음 |
| **C** | **Kafka 유지 + 재시작 복구 구현** | 토픽 계약 유지, 복구가 실제로 됨 | 사건 기록 저장 비용, 중복 처리 규칙 필요 |

**결정: C.** Kafka 를 기본값으로 유지하고, 재시작 복구는 DB 사건 기록으로 합니다.
- **사건 기록**: 단계가 바뀌거나 에이전트가 결과를 쓸 때마다 사건의 작업 상태(작업 정보, 분류, 시도 번호, 질문, 분석·검증·작성 결과, 도구가 본 수치, 단계 기록)를 `agent_incident.checkpoint_json` 에 남깁니다. 결과를 **먼저 기록하고 그다음에 이벤트를 보냅니다.** 사건이 끝나면 기록을 지웁니다(결과는 `agent_analysis` 에 있음).
- **되살리기**: 앱이 켜지면 상태가 TRIAGED·ANALYZING·VERIFYING·WRITING 인 사건을 기록에서 되살리고, 멈춘 단계의 요청 이벤트를 다시 보냅니다(`IncidentStore.restore`, `IncidentOrchestrator.resume`). 시작을 막지 않도록 별도 스레드에서 합니다.
- **중복 처리**: 같은 요청이 두 번 와도(Kafka 재전달, 복구의 재발행) 한 번만 처리합니다. 각 에이전트는 사건 상태와 시도 번호가 맞을 때만 일하고, 이미 결과가 있으면 LLM 을 다시 부르지 않고 완료만 다시 알립니다. 오케스트레이터는 지난 단계의 완료 이벤트를 무시합니다.
- **이어 가지 않는 사건**: 평가 재생 사건(기다리던 요청이 이미 끊김)과 마지막 기록 뒤 `recover-max-age-minutes`(기본 1440분)가 지난 사건은 실패로 닫고, 경보는 다시 분석 대상(`NEW`)으로 돌립니다. 기록이 없는 예전 사건도 실패로 닫습니다.
- 설정: `qg.agent.pipeline.recover`(기본 true), `qg.agent.pipeline.recover-max-age-minutes`.

**왜 Kafka 재전달에만 기대지 않는가**: Kafka 는 처리 중이던 이벤트를 다시 주지만, 그 이벤트가 가리키는 사건 상태(질문·분석 결과)는 Kafka 에 없습니다. 또 되살리기 전에 온 이벤트는 버려질 수 있습니다. 그래서 복구의 기준은 DB 기록으로 두고, Kafka 는 **에이전트를 프로세스로 나눌 때의 토픽 계약**과 **나뉜 프로세스 사이에서 보낸 이벤트를 잃지 않는 전달**을 맡습니다. direct 로 바꿔도 복구는 똑같이 동작합니다.

**확인**: `IncidentRecoveryTest`(분석 결과 기록 뒤 멈춤 → LLM 재호출 없이 이어 감, 분석 중 멈춤 → 그 시도 다시 분석, 되돌림 직후 멈춤 → 시도 번호·지적 유지, 평가 재생·오래된 사건 → 실패로 닫음, 중복 이벤트 무시), 컨테이너 시험(SQL Server 에서 기록 읽기·기록 없는 사건 닫기). 실제 앱을 분석 도중 끄고 다시 켜는 확인은 맥에서 합니다.

## 한계
- 규칙 검증은 "근거가 있는가, 모순이 없는가"를 볼 뿐, 원인이 맞는지는 판단하지 못합니다. 그건 사람 승인이 맡습니다.
- 되돌림이 생기면 그 단계는 LLM 호출이 한 번 더 들어 시간이 늘어납니다. 재생 평가에서 되돌림 횟수와 시간을 함께 기록합니다.
- ~~진행 중인 사건 상태는 메모리에 있어 앱이 재시작되면 사라집니다.~~ → 3단계에서 DB 사건 기록으로 재시작 복구를 넣었습니다. 남은 한계: 사건 상태의 원본은 여전히 한 JVM 의 메모리이고 DB 기록은 복사본입니다. 에이전트를 여러 프로세스로 나누면 각 프로세스가 DB 기록을 원본으로 읽고 쓰도록(또는 Redis 로) 바꿔야 합니다.
- 복구는 "적어도 한 번" 처리입니다. 분석 도중(LLM 호출 중) 멈추면 그 시도는 처음부터 다시 하므로 LLM 호출이 한 번 늘 수 있습니다.
