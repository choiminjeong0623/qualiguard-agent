# ADR-016. 역할 분리형 멀티 에이전트 — Kafka 이벤트로 잇는다

- 상태: 진행 중 (2026-11-15). 1단계 검증 에이전트 구현
- 관련: [ADR-005](ADR-005-spc-detect-llm-reason.md) 탐지는 SPC·판단은 LLM, [ADR-008](ADR-008-agent-design.md) 원인 분석 에이전트

## 배경
지금까지는 원인 분석 에이전트 하나가 사건 묶기 → 조사 → 판단 → 초안 저장을 모두 했습니다. 이 구조에는 두 가지 약점이 있습니다.
1. **자기 검증이 없습니다.** 모델이 도구를 건너뛰거나, 지어낸 사례 번호를 쓰거나, "제품 영향 없음"이라 해 놓고 불량률이 오른 경우를 잡지 못합니다.
2. **단계가 한 함수에 묶여 있습니다.** 어디서 오래 걸리는지, 어디서 실패했는지 따로 보기 어렵고, 보고서 작성만 로컬 모델로 바꾸는 것처럼 단계별로 바꾸기 어렵습니다.

## 결정 (전체 설계)
역할마다 에이전트를 나누고, 넘겨주는 지점마다 Kafka 토픽을 둡니다. 사람 승인은 항상 마지막입니다.

| 에이전트 | 하는 일 | 방식 |
|---|---|---|
| 분류(Triage) | 경보 심각도·유형 판정, 같은 설비 경보를 사건으로 묶음 | 규칙 |
| 원인 분석 | 도구로 근거를 모아 원인 추정 | LLM (Gemini) |
| **검증(Verifier)** | 분석 결과를 데이터와 대조, 약하면 분석으로 되돌림 (횟수 제한) | **규칙** |
| 보고서 작성 | 기밀 데이터가 든 초안 문장 작성 | 로컬 소형 LLM, 실패 시 근거 표 초안 (클라우드로 넘기지 않음) |
| 오케스트레이터 | 사건 상태 관리: 분류 → 분석 → 검증 → 작성 → 사람 승인 | 상태 기계 |

LangGraph 같은 Python 프레임워크 대신 Spring AI + Kafka 로 만듭니다. 이미 데이터 흐름이 Kafka 위에 있고, 8GB 개발 환경에서 런타임을 하나 더 띄우지 않기 위해서입니다.

## 1단계: 검증 에이전트 (구현)
`VerifierAgent` — LLM 을 쓰지 않는 규칙 기반 검증입니다.
- **왜 LLM 이 아닌가**: 분석 1단계가 이미 평균 45~49초라 LLM 검증을 붙이면 1분 목표에서 더 멀어집니다. 또 같은 모델이 자기 답을 다시 읽는 검증은 독립적인 확인이 되기 어렵습니다. 그래서 **모델이 바꿀 수 없는 것**(도구 호출 기록, DB 의 실제 값, 경보 규칙)과 결과를 맞춰 봅니다.
- **규칙은 모두 일반 원칙**입니다. 특정 고장을 맞히기 위한 힌트는 넣지 않습니다.

| 규칙 | 되돌림(FAIL) 조건 |
|---|---|
| 조사 충분성 | 결론(초안·센서 점검)을 냈는데 센서 추이나 불량 조회 도구를 부르지 않음 |
| 근거 수치 | 결론의 근거 중 수치가 담긴 것이 2개 미만 |
| 판단·원인 정합 | 초안인데 원인이 UNKNOWN·NOISE / 지속성 경보인데 NOISE / 관찰인데 watchItems 없음 |
| 과거 사례 실재 | 인용한 사례가 기준 시점까지 승인된 사례에 없음 (지어낸 번호·미래 사례) |
| 데이터 대조 | "제품 영향 없음"(센서 점검)인데 불량률 경보가 있거나, 최근 50 shot 불량률이 앞 250 shot 의 2배 이상이면서 5%p 이상 높음 |

- 되돌릴 때는 지적 문장과 앞선 결과를 붙여 분석 에이전트를 다시 부릅니다. **최대 `verify-max-retries`(기본 1)회**입니다.
- 다시 분석해도 약하면 결과는 그대로 쓰되 `verify_status = WEAK` 로 남기고, 초안이면 근거 끝에 "검증 에이전트: 근거 부족 — …"을 붙여 검토자가 보게 합니다. 판단을 검증 에이전트가 바꾸지는 않습니다(최종 판단은 사람).
- 기록: `agent_analysis.attempts`, `verify_status`, `verify_json`. QMS 화면의 에이전트 분석 기록에 "검증 통과 / 재분석 n회 / 근거 부족" 태그와 지적 내용을 보여 줍니다.

## 한계
- 규칙 검증은 "근거가 있는가, 모순이 없는가"를 볼 뿐, 원인이 맞는지는 판단하지 못합니다. 그건 사람 승인이 맡습니다.
- 되돌림이 생기면 그 단계는 LLM 호출이 한 번 더 들어 시간이 늘어납니다. 재생 평가에서 되돌림 횟수와 시간을 함께 기록합니다.
