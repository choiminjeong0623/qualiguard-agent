# ADR-008. 원인 분석 에이전트: 사건 단위 분석, 지식저장소 기반 추론, 사람 승인

- 상태: 채택
- 날짜: 2026-11-14

## 배경
SPC 이상 탐지가 경보를 내면, 근거를 모아 원인을 추정하고 부적합 보고서 초안을 쓰는 에이전트가 필요합니다. 정해야 할 것은 다음과 같았습니다.
- 경보마다 LLM을 부를지, 묶어서 부를지
- 원인 지식을 어디서 얻게 할지
- AI 판단을 어떻게 믿고 검증할지
- 어떤 기술로 만들지

## 결정

### 1) 경보를 사건 단위로 묶어 분석한다
같은 설비에서 첫 경보부터 **100 shot·30분 안**에 난 미처리 경보를 하나의 사건으로 묶어 LLM을 한 번만 부릅니다. 같은 설비·같은 원인의 초안이 60분 안에 있으면 **새 초안을 만들지 않고 기존 초안에 경보를 연결**합니다.
- 이유: 히터 열화 하나에 경보가 20건 가까이 나는데, 경보마다 부르면 비용이 들고 같은 내용의 보고서가 여러 장 생깁니다.

### 2) 원인-센서 대응표를 프롬프트에 넣지 않는다
"온도↓·압력↑이면 히터"처럼 정답 규칙을 알려 주면 정확도는 오르지만, AI가 추론한 것이 아니라 정답을 받아 적은 것이 됩니다. 대신 **과거 부적합 사례(지식저장소)를 도구로 찾아 당시 근거와 현재 패턴을 비교**하게 했습니다. 실제 현장에서도 원인 지식은 과거 보고서에 쌓여 있습니다.
- 프롬프트에는 "불량 유형만 같고 센서 패턴이 다른 사례는 원인이 다를 수 있다"는 주의만 넣었습니다.

### 3) 조사 절차를 정하고, 근거와 과정을 남긴다
| 단계 | 도구 | 확인하는 것 |
|---|---|---|
| 1 | `getSpcSummary` | 경보 센서 외에 함께 움직인 센서 |
| 2 | `getSensorTrend` | 서서히 변했는지, 단발적으로 튀었는지 |
| 3 | `getDefectSummary` | 실제 불량이 늘었는지, 어떤 유형인지 |
| 4 | `findSimilarNcr` | 과거 사례와 패턴 비교 |
| 5 | `getMaintenanceHistory` | 교체 주기, 미실시 권고 |

- 근거(evidence)에는 도구로 확인한 **실제 수치**를 쓰고, 참고 사례에는 **도구 결과에 있는 번호만** 쓰게 했습니다.
- 모든 분석을 `agent_analysis`에 기록합니다: 판단, 원인 코드, 확신도, 결과 전문, **도구 호출 순서와 인자**, 소요 시간.

### 4) 판단은 세 가지, 확정은 사람이 한다
| 판단 | 조건 | 처리 |
|---|---|---|
| `NCR_DRAFT` | 여러 shot에 걸친 추세나 관련 센서의 동반 변화가 있고 품질 영향이 있거나 예상될 때 | 부적합 초안 생성 (`AI-연도-번호`) |
| `SENSOR_CHECK` | 한 센서 값만 간헐적으로 튀고 다른 센서·불량률은 정상 | 경보 종결, 측정 계통 점검 권고 |
| `OBSERVE` | 단발성 변동 | 경보 종결 |

초안은 `DRAFT` 상태로만 만들어지며, 품질 담당자의 승인을 거쳐야 확정됩니다.

### 5) 기술: Spring AI 2.0 + Gemini, 도구는 저장 프로시저
- 채용 공고의 주력 스택(Java·Spring)과 맞추기 위해 Spring AI를 썼습니다. 도구는 `@Tool` 메서드이고 내부에서 저장 프로시저만 호출합니다.
- 자동 분석은 **기본으로 꺼 두었습니다** (`qg.agent.auto-enabled=false`). 켜면 경보마다 LLM 비용이 발생하므로, 평가와 시연은 API로 수동 실행합니다.

### 6) 승인된 초안은 지식저장소로 돌아간다 — 승인 시점보다 뒤의 분석에서만 (2026-11-15 추가, F-10)
QMS 검토 화면([ADR-009](ADR-009-qms-review-screen.md))에서 승인한 AI 초안은 `APPROVED`가 되어, 다음 분석의 `findSimilarNcr` 검색 대상이 됩니다. 조치를 마치면 실제 조치 내용과 함께 `CLOSED`로 닫습니다.

| 장치 | 이유 |
|---|---|
| 승인에 **확정 원인·원인 코드(UNKNOWN·NOISE 제외)** 필수 | 원인이 빈 사례가 지식저장소에 들어가 다음 판단을 흐리지 않게 |
| 유사 사례 검색에 **분석 기준 시점(`@AsOf`)** 적용: 그 시점까지 승인된 사례만 | 지난 경보를 다시 분석(재생 평가 포함)할 때 **그 뒤에 승인된 사례 = 미래 지식**을 보지 않게. 데이터([ADR-007](ADR-007-sqlserver-qms-schema.md) 결정 4)·경보([장애 분석 04](../troubleshooting/04-agent-evaluation-leakage.md))에 이은 세 번째 누수 경로 |
| 검색 결과에 출처(`source`: 사람 작성 / AI 초안을 사람이 승인)와 원인 코드 | 에이전트가 사례의 신뢰도를 구분할 수 있게 |
| 지식저장소 제거 실험은 **원인 코드 기준**으로 숨김 | 승인된 AI 초안이 늘어도 "정답과 같은 원인의 사례가 없을 때"를 정확히 재현 |

## 결과
- 첫 평가 5/5는 사건 묶기가 첫 경보 이후 경보까지 포함한 유리한 조건이었고, 첫 경보만으로 판단하는 반복 평가에서는 12/15였습니다 ([장애 분석 04](../troubleshooting/04-agent-evaluation-leakage.md)). 건당 35~50초 ([평가 결과](../evaluation.md))
- 개발 중 LLM 연결과 응답 형식 문제를 겪었고, 응답을 직접 해석하는 방식으로 바꿨습니다 ([장애 분석 03](../troubleshooting/03-agent-llm-response-parsing.md))
- 이에 따라 평가를 시간 순 재생 방식으로 바꾸고, 경보 규칙의 의미·확신도 기준·이전 판단 반영을 에이전트에 추가했습니다. 재생 평가 3회 반복 15/15, 과거 사례를 숨긴 실험도 15/15였지만 히터 열화 진단은 첫 불량보다 늦었습니다 ([장애 분석 04 결과](../troubleshooting/04-agent-evaluation-leakage.md)).
