# ADR-019. 늦게 도착한 shot 재판정과 출하 확정 시리얼 연결

- 상태: 채택
- 날짜: 2026-11-22
- 관련: [ADR-017](ADR-017-telemetry-nulls-serial.md) 의 "남은 일" 두 가지

## 배경
ADR-017 에서 두 가지를 미뤄 두었다.

1. **늦게 온 shot**(그 설비에서 이미 판정한 shot 보다 `ts` 가 앞섬)은 저장만 하고 판정하지 않았다.
   그래서 늦게 온 shot 이 개별값 한계를 크게 넘어도, 그 값이 있었다면 평균 이동(X̄)이 잡혔을 구간이어도 경보가 나지 않았다.
2. **출하 확정 시리얼 연결 표**(`shipment_serial_link`)는 만들기만 하고 채우는 로직이 없었다.
   공정 중 임시 시리얼은 겹치므로, 확정 시리얼로 "이 제품을 만든 shot" 을 거꾸로 찾을 수 없었다.

## 1. 늦게 온 shot 재판정

### 고려한 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 지금처럼 저장만 | 단순 | 늦게 온 shot 의 이상을 놓침 |
| B. 실시간 흐름 앞에 순서 맞춤 버퍼(N초 대기 후 ts 순 판정) | 모든 shot 을 시간 순으로 판정 | 모든 경보가 N초 늦어짐. 실시간 핵심 경로가 바뀌어 기존 평가 수치(진단 시점)를 다시 재야 함 |
| **C. 실시간 흐름은 그대로, 늦게 온 shot 만 따로 다시 판정** | 정상 shot 의 경보 지연 0. 늦게 온 shot 의 이상도 잡음 | 다시 볼 수 있는 범위가 보관한 최근 값(30 shot)까지 |

### 결정: C
`SpcEngine.processLate` 가 실시간 상태(부분군·연속 횟수·기준값·최근 값)를 **바꾸지 않고** 따로 판정한다.

| 규칙 | 늦게 온 shot 처리 | 이유 |
|---|---|---|
| INDIVIDUAL (개별값 ±4σ) | 언제 와도 판정 | 값 하나와 기준값만 보면 되므로 순서와 무관 |
| XBAR · S_CHART (5 shot 부분군, 연속 2회) | **최근 30 shot 안이면** 그 값을 시간 순서 자리에 끼워, 그 값을 포함하는 5 shot 구간마다 바로 앞·뒤 5 shot 구간과 함께 '연속 2회'를 다시 봄 | 부분군은 순서가 필요. 실시간이 남겨 둔 최근 30개 값과 그 시각(`recentTs`)으로 순서를 복원 |
| P_CHART (50 shot 불량률) | 기준 불량률이 정해진 뒤면 지금 구간에 넣음 | 개수 비율이라 순서와 무관. 늦게 온 불량을 버리지 않기 위함 |

- 30 shot 보다 더 늦으면 부분군 규칙은 보지 않고 `OUT_OF_WINDOW` 로 표시한다(개별값·불량률은 여전히 판정).
- **경보 중복 방지**: 재판정 경보도 실시간 경보와 같은 반복 억제(규칙·센서별 100 shot)를 거친다. 실시간에서 이미 난 경보는 다시 내지 않는다.
- 재판정 경보의 위치는 늦게 온 shot 자신(`shotNo`, `ts`)이고, 메시지 앞에 `[늦게 도착한 shot 재판정]`, `evidence_json.lateRejudged = true` 를 남긴다.
  분석 에이전트는 다른 경보와 똑같이 처리한다.
- 저장: `process_shot.late_status` = `REJUDGED` / `OUT_OF_WINDOW` (`18_late_shot_rejudge.sql`), 지표 `qg.spc.late_shots{status}`.
- 이전 버전 상태(최근 값의 시각이 없음)는 새 shot 이 30개 쌓일 때까지 `OUT_OF_WINDOW` 로 처리한다.

### 한계
- 30 shot(약 15분, 사이클 30초 기준)보다 늦은 shot 의 부분군 판정은 하지 않는다. 더 넓히려면 DB 의 `process_shot` 에서 시간 순으로 다시 읽어 판정하는 배치가 필요하다.
- 구간을 5가지로 밀어 보므로(그 값을 포함하는 5 shot 구간), 실시간 부분군(도착 순 5개 묶음)보다 경보가 약간 쉽게 난다. 반복 억제로 폭주는 막는다.

## 2. 출하 확정 시리얼 연결

- API `POST /api/qms/shipment/confirm` (`REVIEWER` 만), 화면 `qms/shipment.html`.
- 규칙(`SerialLinkRule`, DB 없이 시험):
  - 연결할 수 있는 shot = 아직 다른 확정 시리얼에 연결되지 않았고 검사 결과가 NG 가 아닌 shot
  - 임시 시리얼로 찾은 그런 shot 이 **하나면 자동 연결**, **여럿이면 후보를 돌려주고 사람이 고른다**(409 `AMBIGUOUS`). 추측해서 붙이지 않는다.
  - 검사 결과가 없는 shot(결측)은 연결하되 경고를 돌려준다.
  - 확정 시리얼은 비어 있지 않고 40자 이하, `TMP-` 로 시작하면 안 된다.
  - 고유성은 DB 고유 인덱스(확정 시리얼, message_id)가 최종 보장. 동시에 확정해 걸리면 409 로 다시 조회하게 한다.
- 추적 `GET /api/qms/shipment/trace/{확정 시리얼}`: 그 제품을 만든 shot 의 공정 값 + shot 시각 앞 30분~뒤 5분 같은 설비 경보와 연결된 부적합(NCR).
  고객 클레임·리콜 때 "이 제품을 만들 때 설비에 무슨 일이 있었나" 를 찾는 용도.

### 한계
- 출하 시스템과의 연계(출하 번호 자동 수신)는 없다. 지금은 사람이 화면·API 로 확정한다.
- 확정 취소(연결 해제) 기능은 없다. 잘못 연결하면 DB 에서 지워야 한다.
