# 03. 향후 계획: 로컬 소형 LLM, 설비 쪽 보안, Redis

- 작성일: 2026-11-15
- 상태: **계획 (미구현)**. 이 문서의 항목은 아직 코드에 없습니다. 수치는 추정이며, 구현할 때 실측으로 바꿉니다.
- 관련: [문제 정의](01-problem-definition.md), [아키텍처](02-architecture.md), [ADR-005 (탐지는 규칙, LLM은 경보 시에만)](decisions/ADR-005-spc-detect-llm-reason.md), [ADR-008 (에이전트 설계)](decisions/ADR-008-agent-design.md), [ADR-011 (QMS 로그인)](decisions/ADR-011-qms-login.md)

이 프로젝트의 대표 강점은 **MQTT·Kafka 실시간 데이터 흐름과 공장 현장에 맞는 구성**입니다. 아래 세 가지는 그 방향에서 다음에 할 일을 정리한 것입니다.

| 주제 | 결정 | 이유 |
|---|---|---|
| 로컬 소형 LLM | **넣는다** | 공장 데이터는 외부 클라우드로 내보내기 어려운 경우가 많다 |
| 설비 쪽 보안 | **MQTT 장비 인증 + 토픽 ACL** | 센서 데이터 시스템의 입구는 사람이 아니라 설비다 |
| Redis | **우선순위 낮음 (지금은 넣지 않음)** | Kafka·기존 중복 제거와 역할이 겹치고 8GB 메모리 부담 |

사람 로그인은 OAuth2/JWT 같은 외부 인증을 넣지 않습니다. QMS 승인 화면에는 이미 폼 로그인과 역할이 있고([ADR-011](decisions/ADR-011-qms-login.md)), 이 시스템의 핵심 위험은 사람 계정보다 **아무 장비나 MQTT 토픽에 값을 쓰는 것**이기 때문입니다.

## 2. M1 8GB 메모리 배분과 모델 크기 (추정)

### 현재 구성 (docker-compose 상한 기준)

| 구성 요소 | 현재 상한 |
|---|---|
| Mosquitto | 64MB |
| Kafka (KRaft, 힙 최대 512MB) | 900MB |
| SQL Server 2025 | 2,500MB |
| Kafka UI (`--profile tools`일 때만) | 400MB |
| qms-app (JVM, 힙 최대 384MB) | 약 550MB (추정) |

### 로컬 LLM을 더할 때 권장 배분

Ollama는 Docker가 아니라 **Mac에서 직접** 실행해야 Apple GPU(Metal)를 씁니다. 모델은 통합 메모리를 GPU와 함께 쓰므로 아래 합계에 그대로 더해집니다.

| 구성 요소 | 권장 | 조정 내용 |
|---|---|---|
| macOS + 터미널·브라우저 | 약 2.5~3.0GB | IDE를 함께 띄우면 더 필요 |
| Docker VM 자체 | 약 0.3GB | |
| Mosquitto | 64MB | 그대로 |
| Kafka | **700MB** (힙 384MB) | 단일 노드·적은 토픽이라 줄일 여지 있음 |
| SQL Server | **2,000MB** | SQL Server 최소 메모리(2GB)에 맞춤, `max server memory` 함께 설정 |
| Kafka UI | **끔** | 필요할 때만 `--profile tools` |
| qms-app | 약 550MB | 그대로 |
| **Ollama + 모델** | **1.3~2.3GB** | 아래 모델 크기 참고 |
| **합계** | **약 7.4~8.5GB** | 8GB에 빠듯함 → 아래 운영 설정이 필요 |

### 모델 크기 추천

| 용도 | 모델 크기 | 예상 메모리 (4비트 양자화 + 문맥 4K) | 판단 |
|---|---|---|---|
| **기본 (항상 쓸 수 있게)** | **1.5B급** (Qwen 계열 1.5B 등) | 약 1.1~1.3GB | 다른 구성과 함께 띄워도 여유가 있다. 정해진 형식의 초안 작성에 맞춘다 |
| 품질이 더 필요할 때 | **3B급** (Llama·Qwen 계열 3B 등) | 약 2.0~2.3GB | 합계가 8GB를 넘을 수 있어, 쓸 때만 올리고 바로 내린다 |
| 비추천 | 4B 이상 / 7B | 3GB 이상 | 스왑이 생겨 전체가 느려진다 |

### 운영 설정 (메모리를 "필요할 때만" 쓰기)

- `OLLAMA_MAX_LOADED_MODELS=1`, `OLLAMA_NUM_PARALLEL=1`: 모델 하나, 요청 하나만
- **`keep_alive`를 짧게(예: 1분)**: 초안은 경보가 났을 때만 만들므로([ADR-005](decisions/ADR-005-spc-detect-llm-reason.md)), 평소에는 모델을 메모리에서 내려 둡니다. 대신 첫 호출에 모델을 올리는 시간(수 초)이 더해집니다
- 문맥 길이 4K로 제한: 도구 조회 결과를 요약해 넣고, 원시 데이터는 넣지 않음
- 측정: `docker stats`, 활동 모니터의 메모리 압력·스왑, 초안 1건 소요 시간을 재생 평가와 함께 기록 (N-10)

## 3. 로컬 / 클라우드 모델 나눠 쓰기 규칙 (초안)

### 데이터 민감도 등급

| 등급 | 예 | 처리 |
|---|---|---|
| **S3 기밀** | 공정 원시값, 설비 설정값·레시피(목표 온도·압력), 설비·라인 실제 이름, 정비 기록 원문, 불량 이미지 | **로컬 전용**. 실패해도 클라우드로 넘기지 않음 (F-13) |
| **S2 내부** | 집계 통계(평균·표준편차·Cpk·불량률), 경보 규칙과 z 점수, 과거 부적합 요약 | **로컬 우선**. 설비 ID 가명화(IMM-01 → EQ-A) 후에만 클라우드 허용 |
| **S1 일반** | 공개 표준·매뉴얼 요약, 일반 품질 용어 설명, 화면 문구 | 클라우드 허용 |

### 작업 종류

| 작업 | 기본 경로 | 이유 |
|---|---|---|
| 부적합 보고서 초안 작성 (현상·원인·조치 문장) | **로컬** | S3 데이터가 들어가고, 형식이 정해져 있어 작은 모델로도 가능 |
| 근거 요약 (도구 결과 → 문장) | **로컬** | 같은 이유 |
| 여러 도구를 오가는 원인 추론 (다단계 도구 호출) | 클라우드 (**S2 이하로 가명화한 경우만**) | 3B 이하 모델은 도구 호출 반복·긴 추론이 약함. 가명화가 안 되면 로컬로 하고 사람 확인 비중을 높임 |
| 일반 문서·매뉴얼 요약, 교육 자료 | 클라우드 | S1 |
| JSON 형식 바로잡기 (재요청) | 원래 작업과 같은 경로 | 내용이 같은 등급이므로 |

### 규칙 적용 순서

1. 입력에 S3 항목이 하나라도 있으면 → 로컬
2. S2이고 가명화를 거쳤으면 → 작업 종류 표를 따름
3. 그 밖에는 → 로컬
4. 모든 호출의 경로·모델·등급을 기록 (F-12)

**현재 구현과의 차이**: 지금 원인 분석 에이전트는 도구 조회 결과(대부분 S2 집계값)와 설비 ID를 그대로 Gemini에 보냅니다. 이 규칙을 적용하면 설비 ID 가명화와 초안 작성의 로컬 전환이 먼저 필요합니다.

## 4. MQTT 장비 인증과 ACL 설계

현재 `infra/mosquitto/mosquitto.conf`는 로컬 개발용으로 `allow_anonymous true`입니다.

```conf
# 예정 설정 (예시)
listener 1883
allow_anonymous false
password_file /mosquitto/config/passwd      # 커밋하지 않음 (mosquitto_passwd 로 생성)
acl_file      /mosquitto/config/acl
```

```conf
# acl (예시) — %u 는 접속한 사용자 이름
# 장비 계정: 자기 설비 토픽에 발행만
pattern write factory/+/%u/telemetry

# 브리지 계정: 모든 설비 텔레메트리 구독
user qg-bridge
topic read factory/+/+/telemetry
```

- 장비 계정 이름을 설비 ID와 같게 두면(`IMM-01`), `%u` 패턴 하나로 "자기 토픽에만 쓰기"를 표현할 수 있습니다
- 시뮬레이터와 브리지는 `.env`의 계정으로 접속하도록 바꿉니다
- 시험: 계정 없음 → 접속 거부, `IMM-01` 계정으로 `IMM-02` 토픽 발행 → 거부, 브리지 외 계정의 구독 → 거부

## 5. Redis를 넣지 않은 이유와 넣는 조건

**지금 이미 중복이 걸러지는 곳**

| 단계 | 방법 |
|---|---|
| MQTT → Kafka | 브리지의 `messageId` 중복 제거 (최근 10만 건) |
| 이상 탐지 | 같은 규칙·센서 경보는 100 shot 동안 다시 내지 않음 (`SpcEngine` 반복 억제) |
| 에이전트 | 같은 설비의 가까운 경보를 하나의 사건으로 묶음, 같은 원인 초안이 있으면 새로 만들지 않고 연결 |
| MES/ERP 연계 | `event_id` 기준 중복 제거 |

그래서 단일 앱 구성에서는 Redis가 맡을 일이 없고, 8GB에서 컨테이너 하나(수백 MB)를 더 띄울 이유도 없습니다.

**넣는 조건**: 앱을 여러 대로 늘려 위 메모리 내 중복 제거가 인스턴스마다 따로 동작하게 되면, 여러 인스턴스가 함께 보는 TTL 저장소가 필요합니다. 이때 `SET key NX EX <초>`로 "같은 설비·규칙·센서 알림은 TTL 안에 한 번만"을 구현합니다 (F-14). 그 전까지는 SQL Server의 고유 키로도 대체할 수 있습니다.

## 6. 면접 답변 정리 (문제 → 해결 → 결과)

**Q. 왜 로컬 모델을 썼나요?** (계획 단계이므로 "결과"는 설계와 검증 기준으로 답합니다)

- **문제**: 공장의 공정 데이터(설정값, 원시 센서값, 설비 정보)는 보안 정책상 외부 클라우드로 보내기 어려운 경우가 많습니다. 그런데 원인 분석 에이전트는 경보마다 이 데이터를 LLM에 보내 보고서 초안을 만듭니다.
- **해결**: 데이터를 민감도 3단계로 나누고, 기밀 데이터가 들어가는 보고서 초안은 노트북에서 도는 소형 오픈소스 모델(Ollama)로, 가명화한 집계값만 클라우드로 보내는 규칙을 세웠습니다. 로컬 모델이 실패해도 클라우드로 넘기지 않고, 근거 표만 담은 초안 틀을 사람에게 넘깁니다. 8GB 메모리 안에서 돌리기 위해 1.5B~3B급 모델을 쓰고, 경보가 날 때만 모델을 올렸다가 내립니다.
- **결과**: 기밀 데이터의 외부 전송을 구조적으로 0건으로 만드는 설계입니다. 작은 모델은 품질이 떨어지므로, 정해진 형식의 문장 작성만 맡기고 판단은 사람 승인으로 보완합니다. 실제 효과는 같은 재생 평가로 "외부 호출 0건, 초안 누락 0건, 메모리·시간"을 재서 확인할 계획입니다.

**Q. 왜 Redis는 안 썼나요?**

- **문제**: 같은 설비에서 같은 알림이 짧은 시간에 여러 번 오면 중복 보고가 생깁니다. 보통 Redis TTL로 막지만, 이 시스템은 Kafka가 이미 데이터 흐름을 맡고 있고 개발 환경이 8GB라 컨테이너를 하나 더 띄우는 부담이 큽니다.
- **해결**: 중복을 단계마다 그 자리에서 막았습니다. MQTT 메시지는 브리지가 messageId로, 경보는 이상 탐지가 100 shot 반복 억제로, 분석은 같은 설비 경보를 한 사건으로 묶어서, MES/ERP 전달은 event_id로 거릅니다.
- **결과**: Redis 없이도 중복 처리가 단계마다 시험으로 확인됐고(같은 메시지 두 번 → 한 번 처리, 같은 연계 이벤트 재발행 → 기록 그대로), 메모리는 SQL Server와 Kafka에 남겼습니다. 다만 앱을 여러 대로 늘리면 메모리 안 중복 제거가 인스턴스마다 따로 돌기 때문에, 그때는 Redis TTL(`SET NX EX`)을 넣는다는 조건을 문서로 남겼습니다.
