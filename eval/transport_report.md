# 에이전트 전달 방식 비교 (로드맵 A2)

- 측정: 2026-11-23 07:07, `./gradlew transportBench` (Kafka localhost:9092)
- 실행 환경: Linux amd64, CPU 4개, Java 21.0.13.0.3 (Kafka 는 docker compose 단일 브로커. 컴퓨터마다 값이 다르니 맥에서 다시 재면 이 파일을 덮어씀)
- LLM 은 즉시 답하는 가짜. 사건 1건 = 분류 → 분석 → 검증 → 작성 → 종결 (이벤트 7개)의 전체 시간

| 전달 방식 | 사건 수 | P50 (ms) | P95 (ms) | 최대 (ms) | 평균 (ms) | 실패 |
|---|---|---|---|---|---|---|
| direct | 200 | 0.43 | 0.71 | 11.18 | 0.58 | 0 |
| kafka | 200 | 47.93 | 56.58 | 76.51 | 49.20 | 0 |

- Kafka 가 더하는 시간(P50): 사건당 약 47.5 ms. 실제 분석 1단계는 평균 40초 이상(LLM)이라 전체 대비 비중은 0.119% 수준. 이벤트 7개마다 생산자 linger.ms=5(묶어 보내기 대기)와 acks=all 확인을 기다리므로 대부분이 그 몫입니다
- 장애 복구: 재시작 복구는 전달 방식과 무관하게 DB 사건 기록(agent_incident.checkpoint_json)으로 합니다 (2026-11-23, 결정 C). 앱이 다시 켜지면 끝나지 않은 사건을 되살려 멈춘 단계의 요청을 다시 보내고, 이미 끝난 일은 다시 하지 않습니다. Kafka 는 기본값으로 유지합니다: 에이전트를 다른 프로세스로 떼어 낼 때의 토픽 계약과, 프로세스가 나뉘었을 때 보낸 이벤트를 잃지 않는 전달(최소 한 번)을 위해서입니다.
- 판단 기록: ADR-016 '3단계: 전달 방식과 재시작 복구'.
